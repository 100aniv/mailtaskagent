### 프로젝트 명

# **메일 기반 업무요청 관리 Agent**

메일로 유입되는 업무 요청을 분석하여 Task로 구조화하고, 선행·후행 메일 및 기존 Task와의 관계를 바탕으로 업무의 생성·변경·회신 대기·완료 등 상태 변화를 지속적으로 관리하는 개인 업무관리 Agent

***

### 배경 및 문제 정의

#### 현재 상황 (As-Is)

업무 요청과 협의사항이 Outlook 메일을 통해 지속적으로 유입되고 있으나, 현재는 사용자가 각 메일을 직접 확인하여 업무 요청 여부와 주요 요청사항을 판단하고 이를 별도로 기억하거나 관리해야 한다.

특히 하나의 업무가 여러 차례의 메일 송수신을 통해 진행되는 경우 최초 요청 이후 추가 요청, 일정 변경, 자료 요청, 회신, 완료 등 업무 상태의 변화를 지속적으로 확인해야 한다.

현재 주요 업무관리 방식은 다음과 같다.

* 메일을 개별 확인하여 업무 요청 여부 판단

* 요청사항, 기한, 요청자 등의 주요 정보 수동 확인

* 신규 업무인지 기존 업무의 후속 요청인지 수동 확인

* 진행 중, 회신 대기, 완료 등의 업무 상태 개별 관리

* 후속 메일에 따른 기한 및 요청사항 변경사항 수동 반영

* 메일함과 개인 기억에 의존한 업무 진행 및 완료 여부 관리

메일은 업무 커뮤니케이션 수단으로는 효과적이지만, 여러 메일에 걸쳐 진행되는 업무의 상태와 변경 이력을 지속적으로 관리하기에는 한계가 있다.

#### Pain Point

**시간 측면**

* 다수의 메일 중 실제 업무 요청을 선별하는 반복 작업 발생

* 요청사항과 기한을 별도로 정리하고 관리해야 함

* 업무 진행상태 확인을 위해 과거 Mail Thread를 반복적으로 조회해야 함

* 후속 요청 및 변경사항을 기존 업무에 수동으로 반영해야 함

**품질 측면**

* 업무 요청 또는 기한을 놓쳐 업무가 누락될 가능성이 있음

* 후속 메일에서 변경된 요청사항이나 기한을 반영하지 못할 수 있음

* 신규 업무와 기존 업무의 후속 요청을 구분하기 어려운 경우가 있음

* 사용자가 수행해야 하는 업무와 상대방 회신을 기다리는 업무를 지속적으로 구분·관리해야 함

* 완료 업무와 진행 중 업무의 변경 이력이 체계적으로 관리되지 않음

**운영 측면**

* 업무관리 품질이 개인의 메일 확인 습관과 기억에 의존함

* 다수 업무가 동시에 진행될 경우 현재 상태와 우선 확인 대상 파악이 어려움

* 장기간 회신이 없거나 기한이 임박한 업무를 선제적으로 확인하기 어려움

#### 기회 요인

업무 메일은 자연어로 작성되며 동일한 요청도 다양한 표현으로 전달되기 때문에 단순 Keyword 또는 고정 Rule만으로 업무의 의미와 상태 변화를 일관되게 판단하기 어렵다.

LLM을 활용하면 메일의 문맥을 분석하여 다음 정보를 구조화할 수 있다.

* 업무 요청 여부

* 주요 요청사항

* 요청자

* 기한

* 회신 필요 여부

* 요청사항 및 일정의 변경 여부

* 완료·취소·추가 정보 요청 등의 의미

본 프로젝트에서는 단일 메일을 분석하는 데 그치지 않고 **새로운 메일, 선행·후행 메일, 현재 Task 상태 및 변경 이력을 함께 분석하여 Agent가 다음 업무 Action을 판단**하도록 구성한다.

예를 들어 다음과 같은 처리가 가능하다.

* 신규 요청 → 새로운 Task 생성

* 기존 업무의 추가 요청 → 기존 Task 업데이트

* 기존 업무의 일정 변경 → Task 기한 수정

* 기존 업무와 관련된 후속 메일 → 해당 Task와 연결

* 추가 자료 또는 회신 대기 상황 → 회신 대기 상태로 변경

* 필요한 정보가 도착한 경우 → 진행 상태로 전환

* 업무 완료가 명확한 경우 → 완료 처리 제안

* 관련 Task 또는 완료 여부가 불명확한 경우 → 사용자 확인 요청

* 업무와 관련 없는 메일 → Task 관리 대상에서 제외

고정 Workflow는 발생 가능한 자연어 표현과 업무 상태 변화를 사전에 조건으로 정의해야 한다. 반면 Agent는 현재 메일과 기존 Task 상태를 함께 분석하여 상황에 적합한 Action을 선택하고, 변경된 상태를 다음 메일의 판단에 다시 활용할 수 있다.

따라서 단순 메일 분류·요약을 넘어 **시간에 따라 변화하는 업무 상태를 지속적으로 추적하고 다음 Action을 결정하는 Agentic AI 기반 개인 업무관리 서비스**를 구현하고자 한다.

***

### 목표 사용자 (Target User)

#### 주요 사용자

Outlook을 주요 업무 커뮤니케이션 수단으로 사용하며 메일을 통해 다수의 업무 요청과 협의를 수행하는 개인 업무 사용자

#### 사용자 업무 특성

* 여러 업무 요청을 동시에 처리함

* 하나의 업무가 여러 차례의 메일 송수신을 통해 진행됨

* 업무별 기한과 현재 진행상태를 지속적으로 관리해야 함

* 추가 정보 또는 상대방 회신을 기다리는 업무가 존재함

* 메일 누락 또는 기한 초과 방지를 위해 메일함을 반복적으로 확인함

* 완료 업무 및 업무 변경 이력을 별도로 관리해야 함

이번 프로젝트에서는 **메일을 주요 업무 요청 채널로 사용하는 개인 업무 사용자 1인**을 1차 Target User로 설정한다.

### 프로젝트 목표

#### 정성적 목표

##### 목표 1. 메일 기반 업무요청 관리 자동화

메일에서 업무 요청과 주요 정보를 자동으로 식별하고 Task로 구조화하여 반복적인 수동 업무 정리를 감소시킨다.

##### 목표 2. 선행·후행 메일 기반 업무 Lifecycle 관리

최초 요청 이후 발생하는 후속 메일을 기존 Task와 연결하여 요청사항, 기한, 회신 대기, 진행, 완료 등 업무 상태 변화를 지속적으로 관리한다.

##### 목표 3. 업무 누락 및 기한 관리 품질 향상

진행 중 업무, 기한 임박 업무, 장기 회신 대기 업무를 Dashboard에서 통합 관리하여 업무 누락 가능성을 낮춘다.

##### 목표 4. Agentic AI 기반 End-to-End 서비스 구현

Agent가 새로운 메일과 현재 Task 상태를 바탕으로 신규 Task 생성, 기존 Task 갱신, 연관관계 연결, 상태 변경 및 사용자 확인 등 다음 Action을 판단하고 결과를 업무관리 Dashboard까지 연결하는 서비스를 구현한다.

테스트 Dataset은 단순 개별 메일 수량보다 **업무의 생성부터 변경·대기·완료까지의 흐름을 포함한 Mail Thread Case**를 중심으로 구성한다.

최종 평가에서는 약 **10****~~15개의 대표 Business Case와 총 20~~****30개 내외의 선행·후행 Mail**을 활용하여 업무 생성, 변경, 연결, 회신 대기, 완료, 무시 및 사용자 확인 등의 상태 변화를 검증한다.

해당 Dataset은 LLM 모델을 직접 학습하거나 Fine-tuning하기 위한 데이터가 아니라, Agent의 판단과 상태관리 기능을 검증하고 KPI를 측정하기 위한 평가 Dataset으로 활용한다.

### 핵심 기능 정의

#### 1. Mail Input 및 업무 정보 구조화

Mail Input 영역을 Agent Core와 분리하고, Agent가 처리할 수 있도록 공통 Mail Input Schema를 정의한다.

AI Master 개발 단계에서는 비식별화·합성 Mail Dataset을 기본 입력으로 사용하며, 구현 일정이 허용되는 경우 테스트용 Gmail을 추가 연동할 수 있다.

향후 실제 사내 적용 단계에서는 동일한 Mail Input Schema를 유지한 상태에서 Microsoft Graph 또는 사내에서 허용된 Connector를 통해 Outlook Mailbox와 연동한다.

Mail Input은 다음 Metadata를 포함한다.

* Mail ID

* Conversation 또는 Thread ID

* 수신·발신 구분

* 발신자 및 수신자

* 제목

* 본문

* 수신 또는 발신 시각

회사에서 제공하는 LLM API는 메일의 자연어 내용에서 다음 정보를 구조화한다.

* 업무 요청 여부

* 주요 요청사항

* 요청자

* 기한

* 회신 필요 여부

* 변경·완료·취소 관련 의미

업무와 관련 없는 메일은 Task 관리 대상에서 제외한다.

#### 2. 선행·후행 메일 및 기존 Task 연관관계 판단

새로운 메일을 현재 Task와 기존 Mail Thread 정보와 비교하여 다음 유형을 판단한다.

* 신규 업무

* 기존 업무의 후속 요청

* 요청사항 추가 또는 변경

* 기한 변경

* 상대방 회신

* 업무 완료 또는 취소 관련 내용

* 업무와 무관한 메일

Conversation 또는 Thread ID와 같은 명확한 Metadata가 존재하는 경우 일반 Rule을 우선 활용한다.

Metadata만으로 판단이 어려운 경우 메일 내용, 요청자, 기존 Task 제목 및 상태를 회사 제공 LLM API에 함께 제공하여 의미적 연관성을 판단한다.

#### 3. Agent 기반 Task Action 및 상태 관리

Agent는 새로운 Mail Context와 현재 Task 상태를 함께 분석하여 다음 Action 중 하나를 선택한다.

| **Action**       | **설명**                   |
| ---------------- | ------------------------ |
| `CREATE_TASK`    | 신규 업무 생성                 |
| `UPDATE_TASK`    | 기존 업무의 요청사항·기한·상태 등 변경   |
| `LINK_TO_TASK`   | 새로운 메일을 기존 Task와 연결      |
| `SET_WAITING`    | 회신 또는 추가 정보 대기 상태로 변경·제안 |
| `MARK_COMPLETED` | 완료 상태 변경 제안              |
| `ASK_USER`       | 판단이 불명확한 경우 사용자 확인       |
| `IGNORE`         | Task 관리 대상이 아닌 메일 제외     |

Task는 다음 상태로 관리한다.

* `TODO`: 해야 할 업무

* `IN_PROGRESS`: 진행 중 업무

* `WAITING_REPLY`: 회신 또는 추가 정보 대기

* `COMPLETED`: 완료 업무

* `CANCELLED`: 취소 업무

LLM과 Agent는 자연어 이해 및 다음 Action 판단을 담당하고, 실제 Task 생성·수정·저장은 일반 Application Logic과 DB에서 수행한다.

완료·취소 처리, 연관관계가 불명확한 Task 연결, 모호한 기한 변경 등 주요 상태 변경은 Agent가 임의로 확정하지 않고 사용자에게 제안하거나 확인을 요청하도록 구성한다.

#### 4. 업무관리 Dashboard 및 사용자 개입

Streamlit 기반 Dashboard에서 업무 상태를 통합 관리한다.

주요 관리 항목은 다음과 같다.

* 해야 할 업무

* 진행 중 업무

* 회신·추가 정보 대기 업무

* 기한 임박 및 기한 초과 업무

* Agent 판단에 대한 사용자 확인 필요 항목

* 완료 및 취소 업무

* Task 변경 이력

사용자는 Dashboard에서 Task의 내용, 기한 및 상태를 직접 수정하고 완료 또는 취소 처리할 수 있다.

사용자가 수정하거나 확정한 정보는 이후 Agent 판단에서 가장 최신의 확정 Task 상태로 활용한다.

#### 5. 기한 및 대기 업무 관리

일반 Application Logic에서 Task의 기한과 현재 상태를 기준으로 다음 업무를 식별한다.

* 당일 마감 업무

* 기한 임박 업무

* 기한 초과 업무

* 일정 기간 이상 회신 또는 추가 정보를 기다리는 업무

AI Master 최종 구현에서는 해당 정보를 Dashboard에서 제공한다.

n8n을 활용한 주기적 Mail 수집, Slack 또는 사내 Messenger Reminder, Daily Brief 등의 기능은 AI Master 최종 제출 이후 실제 사내 적용 및 확장 단계에서 검토한다.

#### 제약사항

**개발환경 제약**

* AI Master 개발은 로컬 PC 등 사용 가능한 외부 개발환경에서 수행할 수 있음

* Python 실행, 필요한 Package 설치 및 Streamlit localhost 실행 가능 여부 확인 필요

* SQLite 파일과 프로젝트 코드의 안정적인 저장 및 Git 버전관리 필요

* 회사 제공 LLM API의 Endpoint, 인증방식 및 외부 개발환경 접근방법 확인 필요

* API Key 및 Token은 코드에 직접 저장하지 않고 환경변수 등으로 분리 관리

**LLM 환경 제약**

* 회사에서 제공하며 외부 개발환경에서도 이용 가능한 LLM API를 사용

* Structured Output 또는 JSON 응답 지원 여부 확인 필요

* JSON 응답을 직접 지원하지 않는 경우 Prompt와 Application Validation을 이용하여 출력 형식 검증

* 동일 입력에서도 판단 결과가 달라질 수 있으므로 Temperature, Prompt 및 출력 Schema 통제

* LLM은 DB를 직접 변경하지 않으며 검증된 Application Logic만 실제 변경을 수행

**Mail Input 제약**

* AI Master 개발 단계에서는 비식별화·합성 Mail Dataset을 기본 입력으로 사용

* 일정과 환경이 허용되는 경우 테스트 전용 Gmail 계정과 합성 메일을 이용하여 실제 Mail Input 연동 가능

* 실제 Outlook 연동은 AI Master 핵심 기능의 필수 성공조건으로 설정하지 않음

* 실제 사내 적용 시 Microsoft Graph, Mailbox 권한, Connector 및 보안정책 검토 필요

**보안 제약**

* 로컬 또는 외부 개발환경에서는 실제 사내 메일, 개인정보, 서버명, IP, 프로젝트명 등의 민감정보를 사용하지 않음

* 회사 제공 LLM API를 사용하더라도 테스트 단계에서는 비식별화·합성 Mail을 우선 활용

* 테스트 Gmail을 사용할 경우 별도의 테스트 계정과 합성 메일만 사용

* 실제 사내 업무메일 처리는 회사에서 승인한 환경과 연동방식으로만 수행

* 중요 Task 변경에는 사용자 확인 절차 적용

**AI 품질 제약**

* 자연어 표현과 문맥에 따라 업무 요청, Mail 연관관계 및 Task 상태 판단 오류가 발생할 수 있음

* Metadata로 확정 가능한 관계는 Rule 기반으로 우선 처리하고 의미 판단이 필요한 경우에만 LLM 활용

* Agent 판단이 불명확한 경우 `ASK_USER`를 통해 사용자가 최종 판단

* 사용자가 직접 수정하거나 확정한 정보는 Agent 예측보다 우선

* 업무 분류, 정보 추출, Task 연결, Action 판단 및 상태 변경 성능을 구분하여 평가
