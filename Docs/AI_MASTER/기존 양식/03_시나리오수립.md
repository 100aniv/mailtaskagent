### 핵심 사용자 시나리오

본 프로젝트는 메일을 통해 발생하는 업무의 주요 Lifecycle인 **신규 업무 생성, 기존 업무 변경, 회신 대기, 진행 재개, 완료·취소 및 사용자 확인**을 중심으로 시나리오를 구성한다.

각 시나리오를 개별 기능으로 중복 구현하지 않고, 다음의 공통 처리 모듈을 재사용하는 구조로 설계한다.

### 공통 처리 모듈

| **모듈**   | **모듈명**                      | **주요 역할**                                                |
| -------- | ---------------------------- | -------------------------------------------------------- |
| **M-01** | Mail Input & Analyzer        | 메일 입력을 공통 형식으로 변환하고 업무 요청 여부, 요청사항, 요청자, 기한 등의 주요 정보를 추출 |
| **M-02** | Task Context Matcher         | 기존 Task 및 선행·후행 메일을 조회하여 현재 메일과의 연관관계를 판단                |
| **M-03** | Agent Action Decision        | 현재 Mail Context와 Task 상태를 바탕으로 다음 Action을 결정             |
| **M-04** | Task State & History Manager | Task 생성·변경, 상태 전이, Mail–Task 연결 및 변경 이력을 저장              |
| **M-05** | User Review & Dashboard      | Agent 판단 결과를 표시하고 사용자의 승인·수정·거절 및 업무현황 관리를 지원            |

## 시나리오 1: 신규 업무 요청 메일의 Task 자동 생성

* **ID:** SC-001

* **상황:** 사용자가 메일을 통해 새로운 업무 요청을 수신한 상황

* **목표:** 메일에서 업무 요청 여부와 주요 정보를 식별하고, 신규 Task를 생성하여 Dashboard에서 관리할 수 있도록 한다.

* **사전 조건:**

  * 외부 개발환경에서도 이용 가능한 회사 제공 LLM API가 준비되어 있어야 한다.

  * 합성·비식별 Mail Dataset 또는 테스트용 Gmail을 통해 메일을 입력할 수 있어야 한다.

  * Task를 저장할 Database와 업무관리 Dashboard가 준비되어 있어야 한다.

  * 사용 가능한 Task 상태가 `TODO`, `IN_PROGRESS`, `WAITING_REPLY`, `COMPLETED`, `CANCELLED`로 정의되어 있어야 한다.

  * Agent가 반환할 Action 및 출력 JSON Schema가 정의되어 있어야 한다.

* **관련 모듈:** M-01 → M-02 → M-03 → M-04 → M-05

### 상세 흐름

| **단계** | **사용자 행동**                                         | **시스템 동작**                                                                                                            | **비고**                                                                    |
| ------ | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1      | 사용자가 업무 요청 메일을 수신하거나 테스트 메일을 입력한다.                 | M-01이 메일을 공통 Mail Schema로 변환하고, 회사 제공 LLM API를 이용해 업무 요청 여부·요청사항·요청자·기한·회신 필요 여부를 추출한다.                               | 초기 구현에서는 합성·비식별 Mail Dataset을 기본 입력으로 사용하고, 일정이 허용되면 테스트 Gmail을 추가할 수 있다. |
| 2      | 사용자는 Agent의 분석 및 판단 결과를 확인한다.                      | M-02가 현재 Task와 동일·유사 업무의 존재 여부를 검색한다. M-03은 검색 결과와 Mail Context를 바탕으로 `CREATE_TASK`, `IGNORE`, `ASK_USER` 중 하나를 결정한다. | 동일 `mail_id`가 이미 처리된 경우 Agent 호출 전에 중복 처리를 차단한다.                          |
| 3      | 사용자는 생성된 업무를 Dashboard에서 확인하고 필요 시 수정하거나 업무를 시작한다. | M-04가 검증된 결과를 DB에 저장하고 Task를 `TODO` 상태로 생성한다. 원본 Mail ID와 Agent 판단 결과를 변경 이력에 저장한다. M-05는 생성된 Task를 Dashboard에 표시한다.  | 사용자가 수정한 정보는 이후 Agent 판단에서 최신 확정정보로 활용한다.                                 |

### 입력 예시

```json
{
  "mail_id": "MAIL-001",
  "conversation_id": "THREAD-001",
  "direction": "INBOUND",
  "sender": "담당자 A",
  "recipients": [
    "사용자"
  ],
  "received_at": "2026-08-18T10:00:00",
  "subject": "DDC 서버 확인 요청",
  "body": "DDC 서버 4대의 패치 적용 여부를 확인하여 이번 주 금요일까지 결과를 공유해 주세요."
}
```

### 기대 출력

```json
{
  "action": "CREATE_TASK",
  "confidence": 0.94,
  "requires_user_confirmation": false,
  "task": {
    "task_id": "TASK-001",
    "title": "DDC 서버 4대 패치 적용 여부 확인 및 결과 공유",
    "requester": "담당자 A",
    "due_date": "2026-08-21",
    "reply_required": true,
    "status": "TODO",
    "source_mail_ids": [
      "MAIL-001"
    ]
  },
  "reason": "업무 수행 요청과 명확한 기한이 포함된 신규 업무 요청 메일로 판단함"
}
```

### 성공 기준

* **기준 1:** 업무 요청 메일 여부를 90% 이상의 정확도로 분류한다.

* **기준 2:** 요청사항·요청자·기한 등 주요 정보를 90% 이상의 정확도로 추출한다.

* **기준 3:** 동일 `mail_id`의 중복 처리로 인한 Task 중복 생성이 발생하지 않는다.

* **기준 4:** 동일 또는 유사한 기존 Task가 존재하는 경우 신규 Task 생성 전에 기존 Task 연결 가능성을 검토한다.

* **기준 5:** 판단 신뢰도가 기준치 미만이거나 신규·기존 업무 여부가 불명확한 경우 `ASK_USER`를 선택한다.

* **기준 6:** Agent 판단 결과가 DB와 Dashboard에 정상 반영되고, 원본 Mail과 Task의 연결 이력이 보존된다.

## 시나리오 2: 후속 메일 기반 기존 Task 연결 및 업무 상태 갱신

* **ID:** SC-002

* **상황:** 기존 Task가 생성된 이후 동일 업무와 관련된 추가 요청, 기한 변경, 자료 요청·회신, 완료 또는 취소 관련 메일이 수신·발신된 상황

* **목표:** 후속 메일을 기존 Task와 연결하고, 메일의 의미와 현재 Task 상태를 바탕으로 요청사항·기한·업무 상태를 적절하게 갱신한다.

* **사전 조건:**

  * 하나 이상의 기존 Task와 연결된 Mail 또는 Task 이력이 존재해야 한다.

  * 입력 메일에 `mail_id`, `conversation_id`, 수신·발신 방향, 발신자, 수신자, 시각, 제목 및 본문 정보가 포함되어야 한다.

  * Task 상태 전이 규칙과 Agent Action이 정의되어 있어야 한다.

  * 합성·비식별 Dataset에는 수신·발신 메일 방향과 처리 순서가 포함되어야 한다.

  * 실제 발신 메일 연동이 없는 경우에는 합성 Outbound Mail을 입력하거나 사용자가 Dashboard에서 회신 대기 상태를 직접 지정할 수 있어야 한다.

* **관련 모듈:** M-01 → M-02 → M-03 → M-04 → M-05

### 상세 흐름

| **단계** | **사용자 행동**                             | **시스템 동작**                                                                                                             | **비고**                                                                   |
| ------ | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1      | 사용자가 기존 업무와 관련된 후속 메일을 수신하거나 발신한다.     | M-01이 후속 메일을 분석하고, M-02가 `conversation_id`, 제목, 요청자, Mail 내용 및 기존 Task 상태를 기준으로 관련 Task 후보를 검색한다.                      | 동일 Thread Metadata를 우선 사용하며, Metadata만으로 판단하기 어려운 경우 LLM이 의미적 연관성을 판단한다. |
| 2      | 사용자는 Agent가 제안한 Task 연결 및 변경 내용을 확인한다. | M-03은 후속 메일과 현재 Task 상태를 분석하여 `UPDATE_TASK`, `LINK_TO_TASK`, `SET_WAITING`, `MARK_COMPLETED`, `ASK_USER` 중 하나를 결정한다.   | 완료·취소, 모호한 기한 변경 등 중요 변경은 신뢰도가 낮으면 자동 반영하지 않는다.                          |
| 3      | 사용자는 변경내용을 승인·수정하거나 필요 시 거절한다.         | M-04는 승인되거나 검증된 변경을 DB에 반영하고 이전 값·변경 값·근거 Mail·변경 시각·Agent 판단 근거를 이력으로 저장한다. M-05는 변경된 Task 상태와 대기기간을 Dashboard에 표시한다. | 완료·취소된 Task도 삭제하지 않고 이력으로 보존한다.                                          |

* **기준 5:** 연관 가능한 Task가 여러 개이거나 판단 신뢰도가 낮은 경우 `ASK_USER`를 선택한다.

* **기준 6:** 상태 변경 전·후 값, 근거 Mail, Agent 판단 및 변경 시각을 100% 이력으로 보존한다.

* **기준 7:** `WAITING_REPLY` 상태가 설정된 기준일을 초과하면 Dashboard에서 장기 대기 업무로 표시한다.

## 시나리오 3: 판단이 불명확한 메일의 사용자 확인

* **ID:** SC-003

* **상황:** 새로운 메일이 기존 업무와 관련된 것으로 보이지만, 연결 가능한 Task가 여러 개이거나 기한·완료·변경 의도가 명확하지 않은 상황

* **목표:** Agent가 불확실한 판단을 임의로 확정하지 않고 사용자에게 관련 Task와 처리 Action을 확인받은 후 결과를 반영하도록 한다.

* **사전 조건:**

  * 하나 이상의 관련 Task 후보가 존재하거나, 메일에 모호한 요청·날짜·완료 표현이 포함되어 있어야 한다.

  * Agent 판단 결과에 `confidence`와 `requires_user_confirmation` 항목이 포함되어야 한다.

  * Dashboard에서 Agent 제안의 승인·수정·거절 및 Task 선택이 가능해야 한다.

* **관련 모듈:** M-01 → M-02 → M-03 → M-05 → 사용자 결정 후 M-04

### 상세 흐름

| **단계** | **사용자 행동**                                   | **시스템 동작**                                                                         | **비고**                                    |
| ------ | -------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| 1      | 사용자가 기존 업무와 관련될 가능성이 있는 모호한 메일을 수신하거나 입력한다.  | M-01이 메일의 요청내용을 분석하고, M-02가 관련 Task 후보를 검색한다.                                      | 동일한 키워드·요청자와 관련된 Task가 여러 개일 수 있다.        |
| 2      | 사용자는 Agent가 제시한 판단과 후보 Task를 확인한다.           | M-03은 연관 Task 또는 처리 Action을 확정하기 어렵다고 판단하여 `ASK_USER`를 선택하고, 후보 Task와 판단 근거를 제시한다. | Agent는 임의로 Task를 연결하거나 상태를 변경하지 않는다.      |
| 3      | 사용자는 관련 Task를 선택하거나 신규 업무 생성·무시·내용 수정을 결정한다. | M-05가 사용자의 선택을 수신하고, M-04가 확정된 결과만 DB와 변경 이력에 반영한다.                                | 사용자 결정은 이후 동일·유사 Mail 처리 시 최신 확정정보로 활용한다. |

### 입력 예시

#### 기존 Task 후보

```json
[
  {
```

### 성공 기준

* **기준 1:** 관련 Task 후보가 여러 개이거나 의미가 불명확한 경우 자동 변경 대신 `ASK_USER`를 선택한다.

* **기준 2:** 사용자에게 후보 Task, Agent 판단 근거 및 선택 가능한 Action을 명확히 제공한다.

* **기준 3:** 사용자의 승인 또는 선택 전에는 Task 상태 및 주요 정보를 변경하지 않는다.

* **기준 4:** 사용자의 선택·수정·거절 결과를 DB와 변경 이력에 보존한다.

* **기준 5:** 사용자가 직접 확정한 정보는 이후 Agent 판단에서 기존 Agent 예측보다 우선한다.

# 시나리오 우선순위 매트릭스

| **시나리오**                                  | **비즈니스 가치** | **구현 난이도** | **PoC 포함** |
| ----------------------------------------- | ----------- | ---------- | ---------- |
| **SC-001 신규 업무 요청 메일의 Task 자동 생성**        | 높음          | 중간         | 예          |
| **SC-002 후속 메일 기반 기존 Task 연결 및 업무 상태 갱신** | 높음          | 높음         | 예          |
| **SC-003 판단이 불명확한 메일의 사용자 확인**            | 높음          | 중간         | 예          |

* **SC-001**은 Mail Input, LLM 정보 추출, Task DB 및 Dashboard를 연결하는 기본 End-to-End 흐름이므로 우선 구현한다.

* **SC-002**는 선행·후행 메일의 관계와 현재 Task 상태를 함께 판단하는 핵심 Agentic AI 시나리오이므로 PoC에 반드시 포함한다.

* **SC-003**은 Agent의 불확실한 판단을 사용자가 검토하는 Human-in-the-loop 시나리오로, 실제 업무 적용의 안전성과 신뢰도를 검증하기 위해 PoC에 포함한다.

* 세 시나리오는 별도의 기능을 각각 중복 구현하지 않고 M-01부터 M-05까지의 공통 처리 모듈을 재사용한다.

* 실제 Outlook 연동, n8n 기반 자동 수집, Slack·사내 Messenger 알림, RAG 및 자동 메일 발송은 본 시나리오의 핵심 범위에 포함하지 않고 이후 확장 단계에서 검토한다.
