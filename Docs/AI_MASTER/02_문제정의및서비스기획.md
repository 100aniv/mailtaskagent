# 02. 문제 정의 및 서비스 기획

## 1. 프로젝트 명

**메일 기반 업무요청 관리 Agent (MailTaskAgent)**

메일로 유입되는 업무 요청을 분석해 Task로 구조화하고, 선행·후행 메일과 현재 Task 상태를 바탕으로 생성·변경·연결·회신 대기·완료 등 업무 Lifecycle을 지속 관리하는 개인 업무관리 Agent다.

## 2. 배경 및 문제 정의

### As-Is

업무 요청과 협의사항이 Outlook 메일을 통해 계속 유입되지만, 사용자는 각 메일에서 요청 여부, 요청사항, 요청자, 기한을 직접 판단하고 별도로 기억하거나 기록한다. 하나의 업무가 여러 메일을 거쳐 진행되면 추가 요청, 기한 변경, 자료 요청·회신, 완료 여부를 과거 Thread와 비교해 수동 반영해야 한다.

### Pain Point

| 관점 | 문제 |
|---|---|
| 시간 | 실제 업무 요청 선별, 과거 Thread 재조회, Task 수동 갱신 반복 |
| 품질 | 요청·기한 누락, 후속 변경 미반영, 신규/기존 업무 오판 |
| 상태 | 수행 중 업무와 상대방 회신 대기 업무를 지속 구분해야 함 |
| 운영 | 개인의 메일 확인 습관과 기억에 의존, 장기 대기·기한 임박 파악 곤란 |

### 핵심 문제 문장

> 비정형 Mail Thread에 흩어진 업무 요청과 상태 변화를 사용자가 수동으로 추적하기 때문에 업무 누락, 기한 변경 미반영, 회신 대기 장기화가 발생한다.

## 3. Agentic AI 적용 이유

고정 Rule은 “부탁”, “월요일”, “전달드립니다” 같은 단어를 처리할 수 있지만, 그것이 신규 요청인지 기존 Task의 변경인지, 어떤 Task와 연결되는지, 현재 대기 상태를 해제해야 하는지는 문맥과 상태를 함께 봐야 한다.

```text
새 Mail
-> 현재 Task + 과거 Mail Context 조회
-> 의미 분석 및 후보 Task 매칭
-> 7가지 Action 중 선택
-> 검증/필요 시 사용자 확인
-> Task와 History 변경
-> 다음 Mail에서 변경된 상태 재사용
```

- Rule/Application Logic: ID, 상태 전이, 검증, DB 반영처럼 확정 가능한 동작
- LLM: 비정형 자연어의 의미, 관계, 변경 의도 해석
- Agent: 현재 상태에 맞는 다음 Action 선택

## 4. 목표 사용자

Outlook을 주요 업무 채널로 사용하고 여러 업무 요청과 협의를 동시에 처리하는 개인 업무 사용자 1인을 8주 프로젝트의 1차 사용자로 설정한다.

## 5. 프로젝트 목표

### 정성 목표

1. Mail에서 업무 요청과 주요 정보를 구조화한다.
2. 선행·후행 Mail을 기존 Task와 연결해 Lifecycle을 관리한다.
3. 기한 임박, 장기 회신 대기, 확인 필요 업무를 Dashboard에서 통합 관리한다.
4. Agent의 판단 근거와 변경 이력을 남기고 중요 결정에는 사용자가 개입한다.

### 정량 KPI

| 지표 | 목표 | 측정 방법 |
|---|---:|---|
| 업무 요청 Mail 분류 정확도 | 90% 이상 | 정답 Label과 Agent 결과 비교 |
| 요청사항·기한 정보 추출 정확도 | 90% 이상 | 정답 필드와 추출값 비교 |
| 신규/기존 Task 연결 정확도 | 85% 이상 | 기대 Task ID와 매칭 결과 비교 |
| Task 상태 변경 판단 정확도 | 85% 이상 | 기대 Action/State와 비교 |
| E2E 시나리오 성공률 | 90% 이상 | 입력부터 Dashboard 반영까지 평가 |
| 업무 정리 소요시간 | 기존 대비 30% 이상 단축 | 동일 Case의 수동/Agent 처리시간 비교 |

KPI는 핵심 사용자 시나리오 3개를 세분화한 대표 Business Case 15개와 합성 Mail 15건을 우선 기준으로 측정한다. 현재 E2E Case·Action 단계 검증을 완료했으며, 분류·필드 추출·Task ID와 수동 처리시간 KPI는 별도 정답 Dataset과 Baseline 측정 후 확정한다.

## 6. 핵심 기능

1. 공통 Mail Schema 및 합성 Dataset 입력
2. 업무 요청 여부와 주요 정보 구조화
3. Thread Metadata와 의미 기반 기존 Task 매칭
4. 7가지 Agent Action 결정
5. 검증·신뢰도·`ASK_USER` 기반 Human-in-the-loop
6. Task/상태/변경 History의 SQLite 저장
7. Streamlit Dashboard의 조회·수정·승인·완료 처리
8. 기한 임박·초과·장기 대기 식별

## 7. 범위

### 8주 필수 범위

- 합성·비식별 Mail Dataset
- LLM API 연동과 구조화 출력
- Mail 분석, Task 생성·매칭·상태 전이
- 7가지 Action과 검증 정책
- SQLite 및 변경 이력
- Streamlit Dashboard와 사용자 개입
- 테스트 Dataset 및 KPI 평가

### 환경·일정 허용 시

- 테스트 Gmail Input Adapter
- 제한적인 Task Matching 고도화
- UI 사용성 고도화

### Post-MVP

- M365 Outlook
- Microsoft Graph 또는 사내 허용 Connector
- n8n
- 사내 운영 DB/Server
- 운영 알림

### 제외

- 자동 메일 발송·삭제·이동
- Calendar 자동 생성
- RAG 사내문서 검색과 첨부파일 정밀 분석
- Multi-Agent, 조직 전체 Mailbox, 다중 사용자 서비스
- 사용자 승인 없는 중요 Task 자동 변경

## 8. 주요 제약과 대응

- Outlook 권한과 Graph App Registration은 필수 성공조건에서 제외한다.
- 실제 연동이 안 되어도 동일 Schema의 합성 Dataset으로 E2E를 완성한다.
- Metadata로 확정 가능한 관계는 Rule을 우선하고 LLM 판단 범위를 줄인다.
- 모호한 관계·기한·완료는 `ASK_USER`로 전환한다.
- API Key는 환경 변수로 관리하고 실제 Mail은 사내 정책에 따라 비식별화한다.
