# 프로젝트 개요

## 프로젝트명

MailTaskAgent는 메일로 유입되는 업무 요청을 분석해 Task로 구조화하고, 후속 메일과 현재 상태를 바탕으로 업무 Lifecycle을 관리하는 개인 업무관리 Agent입니다.

## 기술 스택

Python 3.12.14, 회사 LLM API(gpt-4.1-mini), Pydantic, SQLite, Streamlit, pytest, Gmail API 기반으로 구현했습니다.

## 주요 기능

메일 의미 구조화, 기존 Task 연결, 7개 Action 기반 상태 전이, Human-in-the-loop 검토, Gmail 승인 발송, Dashboard 이력 추적을 제공합니다.

## 기대 효과

업무 누락과 기한 변경 미반영을 줄이고, 회신 대기·진행·완료 상태를 통합 관리해 메일 기반 업무 정리 부담을 낮추는 것이 목표입니다.

# 서비스 아키텍처

## 입력 계층

합성·비식별 Mail Dataset과 테스트 Gmail이 공통 Mail Input으로 유입됩니다.

## 분석 계층

M-01은 메일을 정규화하고 회사 LLM API로 업무 요청 여부, 요청사항, 기한, 의도를 구조화합니다.

## 매칭 및 판단 계층

M-02는 conversation_id 우선 매칭과 top-k Task Context 검색을 수행하고, M-03은 관계·대상 Task·Action을 제안한 뒤 Python Guard가 안전성을 검증합니다.

## 실행 및 저장 계층

M-04는 검증된 Action만 SQLite에 반영하고 Task, Mail 링크, History, Processing Event를 저장합니다.

## 사용자 인터페이스 계층

M-05 Streamlit Dashboard는 업무 현황, 검토 요청, 변경 이력, Agent Trace와 사용자 승인 흐름을 제공합니다.

## 핵심 데이터 흐름

1. 메일 입력을 공통 Schema로 정규화하고 중복 mail_id를 확인합니다.

2. LLM이 메일 의미와 Intent를 구조화합니다.

3. 기존 Thread 또는 제한된 Task·Mail·History Context에서 후보를 검색합니다.

4. Agent가 Action을 제안하고 Python이 Payload, 상태 전이, 승인 조건을 검증합니다.

5. 검증 통과 시 SQLite에 반영하고, 불명확하면 ASK_USER로 전환합니다.

6. 결과를 Dashboard와 운영 로그에 표시하고, 필요 시 회신 Draft와 승인 발송까지 연결합니다.

# 핵심 기능 및 Agent 구현 내용

## 핵심 기능

### 메일 의미 구조화

회사 LLM API와 Structured Output을 사용해 업무 요청 여부, 요청사항, 기한, Intent를 정형 데이터로 변환했습니다.

### Task Context 매칭

동일 conversation_id를 우선 사용하고, 확정이 어려운 경우 SQLite의 Task·최근 Mail·History top-k를 검색해 후보를 좁혔습니다.

### Agent Action 결정

Task Context Agent가 관계·대상·Action을 제안하고, Python이 후보 범위·Intent·상태 전이·중요 변경 승인 조건을 검증했습니다.

### 안전한 실행 및 이력 관리

Pydantic 검증을 통과한 결과만 SQLite Transaction으로 반영하고, 변경 전후 값과 판단 근거를 History와 Processing Event로 남겼습니다.

### Gmail 승인 발송

회신 필요 시 Reply Planning, 사용자 입력 기반 Draft 생성, Allowlist·원본 Thread·명시적 승인 조건을 만족한 경우에만 발송하도록 구현했습니다.

## 사용 기술/라이브러리

* Python — 전체 Agent Workflow와 Application Logic 구현

* 회사 LLM API / gpt-4.1-mini — 메일 의미 분석과 Action 판단 보조

* Pydantic — Structured Output 검증과 상태 데이터 모델링

* SQLite — Task, Mail, History, Processing Event 저장

* Streamlit — Dashboard, 검토 요청, Agent Trace UI 구현

* pytest — 합성 시나리오, 회귀 테스트, 수용 테스트 자동화

* Gmail API — 테스트 메일 수신·Thread 추적·승인 발송 검증

# 기술 문제 해결 과정

### 프롬프트 환각과 모호한 표현 처리

1. 문제 상황: 모델이 “다음 주 중”, “거의 끝난 것 같다” 같은 표현을 특정 날짜나 완료 상태로 과도하게 확정할 수 있었습니다.

2. 원인: 자연어의 모호성이 크고, 메일 본문만으로는 확정 근거가 부족했습니다.

3. 해결 방법: Prompt에 모호한 날짜·완료 예시를 명시하고, 원문 Marker를 Python Guard가 다시 검사해 ASK_USER로 전환했습니다.

4. 결과: 중요 상태 오판을 줄이고 불확실한 Case를 안전하게 사용자 검토로 이관했습니다.

### 구조화 출력과 DB 안전성 확보

1. 문제 상황: LLM JSON이 Schema와 다르면 잘못된 후속 로직이 실행될 위험이 있었습니다.

2. 원인: 응답 형식 불안정과 필수 필드 누락 가능성이 존재했습니다.

3. 해결 방법: Pydantic Validation과 1회 재시도, SQLite Transaction Rollback 정책을 적용했습니다.

4. 결과: Schema 오류·API 실패 시 Task, Link, History를 반영하지 않고 Fail-closed로 처리했습니다.

### 복수 후보 Task 연결 문제

1. 문제 상황: 유사한 활성 Task가 여러 개 있을 때 잘못된 업무에 연결될 위험이 있었습니다.

2. 원인: 제목과 주제가 비슷한 메일만으로는 단일 정답을 확정하기 어려웠습니다.

3. 해결 방법: conversation_id 우선 규칙, top-k Task Context 검색, Query Rewrite 1회, 저신뢰 시 ASK_USER 정책을 적용했습니다.

4. 결과: 임의 자동 변경 대신 안전한 사용자 확인 흐름을 구현했습니다.

### 운영 동시성과 SQLite 안정성

1. 문제 상황: Dashboard와 Windows Scheduler가 동시에 SQLite에 접근하면 잠금 충돌 위험이 있었습니다.

2. 원인: 로컬 단일 DB를 여러 프로세스가 공유하는 구조였습니다.

3. 해결 방법: WAL, 30초 Busy Timeout, synchronous=FULL, OS 단일 실행 잠금, 무결성 점검을 적용했습니다.

4. 결과: 무인 동기화와 UI 접근을 함께 운용하는 안정성을 확보했습니다.
