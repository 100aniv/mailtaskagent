# 프로젝트 개요

## 프로젝트명

MailTaskAgent — 메일 기반 업무요청을 Task로 구조화하고 상태 전이와 회신 대기까지 관리하는 개인 업무관리 Agent 서비스입니다.

## 기술 스택

Python 3.12, 회사 LLM API(gpt-4.1-mini), Pydantic, SQLite, Streamlit, pytest, 테스트 Gmail Adapter를 사용했습니다.

## 주요 기능

메일 의미 분석, 신규/기존 Task 판단, 7개 Action 기반 상태 관리, Human-in-the-loop 승인, Dashboard 추적, 승인 기반 Gmail 발송을 구현했습니다.

## 기대 효과

업무 요청 누락과 기한 변경 미반영을 줄이고, 회신 대기·진행·완료 상태를 한 화면에서 관리할 수 있도록 돕습니다.

# 서비스 아키텍처

## 입력 계층

합성·비식별 Mail Dataset과 테스트 Gmail이 공통 Mail Input으로 유입됩니다.

## 분석 계층

M-01이 메일 의미와 Intent를 구조화하고, M-02가 conversation_id 우선 및 SQLite 기반 Task Context를 검색합니다.

## 판단 계층

M-03이 관계·대상 Task·Action을 제안하고, Python Safety Guard가 Payload·상태 전이·중요 변경을 검증합니다.

## 저장 및 실행 계층

M-04가 검증된 결과만 SQLite에 반영하고 History·Processing Event를 저장한 뒤 재조회로 실제 결과를 확인합니다.

## 사용자 인터페이스 계층

M-05 Streamlit Dashboard가 자동 반영 결과, 검토 요청, 운영 로그, Agent Trace와 회신 초안을 제공합니다.

## 핵심 데이터 흐름

1. 새 Mail 입력 → M-01 구조화 분석

2. Task 후보 검색 → 동일 Thread 우선, 필요 시 top-k Context 검색

3. Action 제안 → Python Guard 검증 → 자동 실행 또는 ASK_USER 전환

4. SQLite 저장 → 재조회 관찰 → Dashboard 반영

5. 회신 필요 시 Draft 생성 → 사용자 승인 후 Gmail 발송

# 핵심 기능 및 Agent 구현 내용

## 핵심 기능

### 메일 의미 구조화

업무 요청 여부, Intent, 요청사항, 기한, 회신 필요 여부를 구조화 출력으로 추출했습니다.

### Task 연결 및 Action 결정

동일 Thread는 규칙 기반으로 확정하고, 모호한 경우 SQLite Task Context RAG와 별도 Agent로 관계·대상 Task·Action을 판단했습니다.

### 안전한 상태 변경

완료·취소·기한 단축 등 중요한 변경은 승인 Gate를 두고, Python Guard가 검증한 결과만 DB에 반영했습니다.

### E2E 서비스 및 회신 처리

메일 입력부터 Dashboard 반영, Reply Planning, Draft 생성, 사용자 승인 Gmail 발송까지 연결했습니다.

## 사용 기술/라이브러리

* Python — Agent workflow와 Application Logic 구현

* 회사 LLM API (gpt-4.1-mini) — 메일 의미 분석과 Action 제안

* Pydantic — Structured Output 검증과 상태 계약 관리

* SQLite — Task, Mail, History, Processing Event 저장

* Streamlit — 실제 업무/시연 모드 Dashboard 구현

* pytest — 회귀 테스트와 시나리오 검증

* Gmail API Adapter — 테스트 메일 수집과 승인 발송 검증

# KPI 달성도

## 달성 항목

* 업무 요청 Mail 분류 정확도 — 90% 이상 → 100% (15/15, 111%)

* 요청사항·기한 추출 정확도 — 90% 이상 → 100% (26/26, 111%)

* 신규/기존 Task 연결 정확도 — 85% 이상 → 100% (8/8, 118%)

* Action 단계 일치율 — 85% 이상 → 100% (28/28, 118%)

* E2E 시나리오 성공률 — 90% 이상 → 100% (15/15, 111%)

## 미달성 항목

* 업무 정리 소요시간 — 기존 대비 30% 이상 단축 → 미측정 (달성률 산정 불가)

비교 가능한 실제 Baseline이 없어 동일 사용자 기준의 순서 효과를 제거한 측정 설계를 후속 과제로 남겼습니다.

# 기술 문제 해결 과정

## 주요 문제 해결 사례

### 모호한 기한·완료 표현의 오판

1. 문제 상황 — LLM이 '다음 주 중', '거의 끝난 것 같다' 같은 표현을 확정적으로 해석하는 경우가 있었습니다.

2. 원인 — 자연어 해석만으로 모호성을 충분히 제어하지 못했고, 완료·기한 계약이 느슨했습니다.

3. 해결 방법 — Prompt에 모호한 표현 예시를 추가하고 원문 Marker Guard와 ASK_USER 전환 규칙을 적용했습니다.

4. 결과 — 불명확한 기한·완료는 자동 반영 대신 사용자 확인으로 이관되었고 Live 평가 15/15, 28/28을 유지했습니다.

### 구조화 출력 오류와 부분 저장 위험

1. 문제 상황 — LLM 응답 JSON이 Schema와 어긋나면 후속 로직이 실패할 수 있었습니다.

2. 원인 — Structured Output 계약과 Validation 실패 대응이 부족했습니다.

3. 해결 방법 — Pydantic Validation, 1회 재시도, SQLite Transaction Rollback, 실패 시 DB 무변경 정책을 적용했습니다.

4. 결과 — Schema/API 실패 시 Task·Link·History가 부분 저장되지 않도록 통제했습니다.

### 복수 후보 Task의 오연결 위험

1. 문제 상황 — 비슷한 주제의 활성 Task가 여러 개일 때 잘못된 Task에 조용히 연결될 위험이 있었습니다.

2. 원인 — 단순 유사도만으로는 대상 Task를 안전하게 확정하기 어려웠습니다.

3. 해결 방법 — conversation_id 우선 규칙, top-k Task Context 검색, Query Rewrite 1회, 최종 불확실 시 ASK_USER를 적용했습니다.

4. 결과 — 복수 후보를 안전하게 구분할 근거가 부족한 경우 자동 변경 0건을 유지했습니다.

### SQLite 동시 접근 문제

1. 문제 상황 — Dashboard와 Scheduler가 동시에 SQLite에 접근할 때 잠금 경합이 발생했습니다.

2. 원인 — 단일 파일 DB 특성상 동시 쓰기 경쟁이 발생했습니다.

3. 해결 방법 — WAL, 30초 Busy Timeout, synchronous=FULL, OS 단일 실행 잠금을 적용했습니다.

4. 결과 — 운영 자동화와 무결성 점검 흐름을 안정화했고 quick_check=ok를 확인했습니다.

# 향후 개선 및 확장 방향

## 단기 개선 (1~3개월)

* 실제 사용자 3~5명을 대상으로 수동 대비 업무 정리시간 Baseline 측정 설계 수행

* 실패·사용자 수정 Case를 평가 Dataset에 반영해 회귀 테스트 고도화

* 실제 Mailbox 일반화 성능 검증을 위한 파일럿 운영 준비

* Reply Planning과 Draft 품질 평가 항목 세분화

실측 KPI와 실패 패턴 데이터가 쌓이면 현재 합성 중심 검증의 한계를 줄이고 서비스 신뢰도를 높일 수 있습니다.

## 장기 확장 (6개월+)

* Microsoft Graph 또는 사내 허용 Connector 기반 Outlook 연동

* 사내 인증, 승인 DB, 서버 배포, 운영 알림 체계 도입

* 사내 문서·첨부파일 검색 RAG와 Vector DB 검토

* 다중 사용자, SSO, 조직 단위 업무관리 서비스로 확장

* Reply-All, CC/BCC, 첨부파일·HTML·서명 자동 처리 지원

입력 소스와 저장 경계를 확장하되 현재 Agent Core와 Safety Guard 구조를 유지하는 방향으로 발전시킬 계획입니다.
