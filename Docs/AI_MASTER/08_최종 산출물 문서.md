프로젝트 개요
프로젝트명
MailTaskAgent는 메일 기반 업무 요청을 Task로 구조화하고, 후속 메일과 현재 상태를 바탕으로 생성·변경·연결·회신 대기·완료까지 관리하는 개인 업무관리 Agent다.

기술 스택
Python, 회사 LLM API(gpt-4.1-mini), OpenAI Python SDK, Pydantic, SQLite, Streamlit, pytest, Gmail Adapter를 중심으로 구현했다.

주요 기능
메일 의미 분석, 기존 Task 연관관계 판단, 7개 Action 기반 상태 전이, 사용자 확인(ASK_USER), 변경 이력 저장, Dashboard 조회, 승인 기반 회신 발송을 지원한다.

기대 효과
업무 요청 누락과 기한 변경 미반영을 줄이고, 기한 임박·회신 대기 업무를 한 화면에서 관리할 수 있다. 실측 검증에서는 15개 합성 Case와 테스트 Gmail 기준 높은 일관성을 확인했다.

서비스 아키텍처
입력 계층
합성·비식별 Mail Dataset과 테스트 Gmail이 공통 Mail Input Schema로 유입된다.

분석 계층
M-01이 메일 의미와 Intent를 구조화하고, M-02가 conversation_id 우선 규칙과 SQLite 기반 Task Context 검색을 수행한다.

판단 계층
Task Context Agent가 관계·대상 Task·Action을 제안하고, Python Safety Guard가 Payload·상태 전이·중요 변경을 검증한다.

저장 및 실행 계층
M-04가 검증된 결과만 SQLite에 반영하고, Task·Mail·History·Processing Event를 저장한 뒤 재조회로 실제 반영 상태를 확인한다.

사용자 인터페이스
M-05 Streamlit Dashboard가 내 업무, 검토 요청, 운영 상태, 변경 이력, Agent Trace와 사용자 승인 흐름을 제공한다.

핵심 데이터 흐름
새 메일이 입력되면 M-01이 업무 요청 여부, 요청사항, 기한, Intent를 구조화한다.

M-02가 동일 Thread를 우선 확인하고, 확정 불가 시 SQLite Task·최근 Mail·History에서 top-k 후보를 검색한다.

Task Context Agent가 관계·대상·Action을 제안하고 Python Guard가 후보 범위, Intent, 상태 전이, 위험도를 검증한다.

안전한 결과는 SQLite에 반영하고, 중요하거나 불명확한 결과는 ASK_USER로 전환한다.

Dashboard에 최종 상태와 이력을 반영하고, 필요 시 승인 기반 회신 Draft 생성과 Gmail 발송으로 이어진다.

핵심 기능 및 Agent 구현 내용
핵심 기능
메일 의미 분석
회사 LLM API로 메일의 업무 요청 여부, 요청사항, 기한, Intent를 구조화했다. 모호한 날짜·완료 표현은 Guard와 ASK_USER로 통제했다.

Task Context 매칭
conversation_id를 우선 사용하고, 확정 불가 시 SQLite의 Task·최근 Mail·History top-k를 검색해 기존 업무와의 관계를 판단했다.

Action 결정과 상태 관리
CREATE_TASK, UPDATE_TASK, LINK_TO_TASK, SET_WAITING, MARK_COMPLETED, ASK_USER, IGNORE의 7개 Action과 5개 상태 전이를 구현했다.

Safety Guard와 Human-in-the-loop
LLM 제안은 그대로 실행하지 않고 Python이 Payload, 후보 범위, 상태 전이, 중요 변경을 검증한다. 완료·취소·기한 단축처럼 위험도가 큰 변경은 사용자 승인 후 반영한다.

Dashboard 및 회신 기능
Streamlit에서 내 업무, 검토 요청, 운영 로그, Agent Trace를 확인할 수 있게 했고, 승인 기반 Gmail 회신 Draft 생성과 발송까지 연결했다.

기술 문제 해결 과정
문제 사례
모호한 날짜·완료 표현 오판
문제 상황: LLM이 “다음 주 중”, “거의 끝난 것 같다” 같은 표현을 특정 날짜나 완료로 과도하게 확정할 수 있었다.

원인: 자연어 해석만으로는 모호한 표현과 명확한 상태 전이를 안정적으로 구분하기 어려웠다.

해결 방법: Prompt에 모호한 날짜·완료 규칙을 명시하고, 원문 Marker Guard와 ASK_USER 전환 로직을 추가했다.

결과: 중요 상태 훼손 가능성을 줄였고, 합성·비식별 평가에서 15/15 실행 단위와 28/28 Action 단계를 유지했다.

구조화 출력 불안정
문제 상황: LLM 응답 JSON이 Schema와 어긋나면 후속 로직이 중단되거나 잘못 실행될 위험이 있었다.

원인: 자유도 높은 응답 형식과 필수 필드 누락 가능성 때문이었다.

해결 방법: Pydantic Validation, 1회 재시도, 최종 실패 시 DB 무변경 Fail-closed 정책을 적용했다.

결과: 구조화 실패가 있어도 Task·Link·History가 부분 반영되지 않도록 통제했다.

SQLite 동시성 충돌
문제 상황: Dashboard와 1분 주기 Gmail Scheduler가 같은 SQLite를 동시에 쓰며 잠금 경합이 발생했다.

원인: 단일 파일 DB 특성상 동시 쓰기 상황에서 lock 충돌 가능성이 있었다.

해결 방법: WAL, 30초 Busy Timeout, synchronous=FULL, OS 단일 실행 잠금과 무결성 점검을 적용했다.

결과: 운영 안정성을 높였고 테스트 Gmail 수용시험과 실제 E2E 재검증을 이어갈 수 있었다.
