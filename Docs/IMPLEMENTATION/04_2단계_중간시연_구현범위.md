# 04. 2단계 중간시연 구현범위

## 1. 목적

1단계의 Create/Update Vertical Slice를 M-01~M-05 공통 구조로 확장하여, 주요 Agent Core와 주요 Action·상태 전이가 실제 Business 흐름에서 동작하는지 검토한다.

1~9절은 구현 목표를 정의하고, 실제로 실행·검증한 결과만 10절 증적에 기록한다.

## 2. 대상 사용자 시나리오

- SC-001 신규 요청 Mail -> 신규 Task 생성
- SC-002 후속 Mail -> 기존 Task 연결·내용/기한/상태 변경
- SC-003 불확실한 Mail -> 사용자 확인

## 3. 주요 시연 흐름

| 흐름 | 입력 예시 | 기대 Action/상태 |
|---|---|---|
| 신규 업무 | 명확한 요청과 기한 | `CREATE_TASK` -> `TODO` |
| 기한 변경 | 동일 Thread의 연장·단축 요청 | `UPDATE_TASK` + 전·후 History |
| 후속 정보 연결 | 기존 업무 관련 추가 Mail | `LINK_TO_TASK` |
| 회신 대기 | 사용자가 자료를 요청한 발신 Mail | `SET_WAITING` -> `WAITING_REPLY` |
| 자료 도착 | 대기하던 자료의 수신 Mail | `UPDATE_TASK` -> `IN_PROGRESS` |
| 모호한 관계 | 관련 Task 후보 2개 | `ASK_USER` |
| 일반 공지 | 별도 조치 불필요 | `IGNORE` |
| 완료 제안 | 완료가 명확한 Mail | `MARK_COMPLETED` 제안 경로 확인 |

`MARK_COMPLETED`의 사용자 승인, 취소 처리와 전체 회귀 검증은 3단계에서 최종 확정한다.

## 4. 모듈별 2단계 범위

### M-01

- 수신·발신 방향을 포함한 합성 Dataset 처리
- 변경·완료·취소·추가 정보 요청 의도 추출
- API Timeout, 비정상 JSON, 필수 필드 누락 처리
- 동일 `mail_id` 재처리 방지

### M-02

- 동일 Conversation 우선 매칭
- 제목·요청자·활성 상태를 결합한 후보 순위
- 제한된 후보에 대한 회사 LLM 의미 판단
- 후보 0개·1개·복수 Case 분기

### M-03 및 Validation

- 7 Action 전체를 Schema Enum으로 지원
- 중간시연 필수: Create, Update, Link, Waiting, Ask, Ignore
- 완료 제안 경로: `MARK_COMPLETED`
- 날짜, Task ID, Payload, 상태 전이, 승인 필요 정책 검증

### M-04

- Mail, Task, Link, History, Processing Result 저장
- `TODO`, `IN_PROGRESS`, `WAITING_REPLY`, `COMPLETED`, `CANCELLED` 상태 지원
- Task/Link/History Transaction과 Rollback
- 사용자 결정과 재처리 상태 기록

### M-05

- 확인 대기 Queue
- 후보 Task, 근거, 신뢰도 비교
- 승인·수정·거절/무시
- 상태별 Dashboard, History, 오류/재처리 표시

## 5. 2단계 데이터 범위

- 대표 Business Case 7~9개
- Case당 1~3개 Mail
- 신규, 후속, 발신, 대기, 자료 도착, 모호성, 공지 포함
- 입력 Dataset과 기대 Action/Task/상태를 별도 파일로 분리

10~15개 최종 Dataset과 KPI 실측은 3단계 범위다.

## 6. 테스트 Gmail 선택 조건

테스트 Gmail은 아래 조건을 모두 만족할 때만 선택적으로 추가한다.

1. 합성 JSON Adapter 기반 M-01~M-05가 안정적으로 동작한다.
2. 별도 테스트 계정과 합성 Mail만 사용한다.
3. Gmail Adapter가 공통 Mail Schema만 출력하며 Agent Core를 변경하지 않는다.
4. 일정 지연 시 즉시 제외할 수 있다.

테스트 Gmail 미구현은 2단계 실패가 아니다.

## 7. 권장 구현 순서

1. 1단계 코드와 데이터 Migration 점검
2. Mail-Task Link와 Processing Result 저장
3. M-02 후보 검색 확대
4. Link/Waiting/Ignore Action
5. User Review와 `ASK_USER`
6. 자료 도착 상태 전이
7. 완료 제안 경로
8. 대표 Case 자동 테스트
9. 중간시연과 한계·이슈 기록

## 8. 2단계 완료 조건

- M-01~M-05가 공통 State로 연결된다.
- SC-001/002/003 대표 흐름을 시연할 수 있다.
- 주요 Action과 Task 상태가 기대 흐름대로 저장된다.
- 복수 후보·모호한 기한·중요 변경은 자동 적용되지 않는다.
- 사용자 승인·수정·거절이 History에 남는다.
- 동일 Mail 재실행이 중복 Task/History를 만들지 않는다.
- 실패 Case가 DB를 잘못 변경하지 않고 나머지 Case 실행을 막지 않는다.

실제 완료와 테스트 결과는 실행 후 기록한다.

## 9. 2단계 제외 범위

- 목표 KPI의 최종 달성 판정
- 최종 10~15개 Case 전체 회귀
- 실제 Outlook, Microsoft Graph, n8n
- 사내 DB·인증·서버 배포·다중 사용자
- RAG, Vector DB, Multi-Agent, LangGraph 필수화

## 10. 2026-08-25 구현 및 검증 증적

### 실제 구현

- `LINK_TO_TASK`: 관련성은 명확하지만 상태 변경이 불필요한 후속 Mail 연결
- `SET_WAITING`: 발신 `MAIL-003` 처리 시 `WAITING_REPLY`와 `waiting_since` 저장
- 자료 도착: `MAIL-004` 처리 시 `IN_PROGRESS` 복귀와 `waiting_since` 해제
- `IGNORE`: 일반 공지와 Mail 본문 Prompt Injection을 Task 변경 없이 처리
- `ASK_USER`: 후보 2개에서 자동 변경 중단, 연결·신규 생성·무시 사용자 결정
- `MARK_COMPLETED`: 완료 제안 후 자동 변경 중단, 사용자 승인 시에만 `COMPLETED`
- 취소 요청: `ASK_USER`로 자동 변경 중단, 사용자 승인 시 `UPDATE_TASK/CANCELLED`
- SQLite 기존 DB에 `waiting_since`를 추가하는 안전한 Migration
- 빠른 시연 4종과 직접 처리, 확인 필요, 현재 업무/History, 실행 로그로 UI 재구성
- 제품형 기본 화면을 `업무 현황`으로 변경하고 `메일 처리함`에서 입력 Source 전체의
  분류, 처리 상태, Action, 연결 Task를 통합 표시
- 미처리 합성메일 전체 자동 정리 기능과 Case별 실패 격리
- 멘토 시연 버튼은 실제 업무 화면과 분리된 `데모 도구`에 유지
- 입력 Dataset과 분리된 기대결과 10개를 `data/scenario_expectations.json`에 저장
- LLM 구조화 출력 오류 시 설정된 1회 재시도

### 실제 검증

- pytest: `20 passed`
- 회사 LLM API Live:
  `MAIL-001 CREATE_TASK` -> `MAIL-003 SET_WAITING` ->
  `MAIL-004 UPDATE_TASK/IN_PROGRESS` -> `MAIL-009 MARK_COMPLETED/승인 대기`
- Streamlit AppTest: 회신 대기/재개 원클릭 시연, 완료 제안 표시, 사용자 승인 후
  `COMPLETED`와 History 저장, 화면 Exception 0건
- 회사 LLM API Live: 취소 의도 추출 -> `ASK_USER` -> 사용자 승인 후 `CANCELLED`
- Secret은 UI·DB·Processing Event에 기록하지 않고 마스킹 테스트 통과

### 남은 2단계 및 3단계 연결 항목

- 제목·요청자·활성 상태를 결합한 후보 점수와 제한적 LLM 의미 비교 고도화
- 모호한 기한, 불명확한 완료, 기한 단축과 다양한 취소 표현 등 추가 대표 Case
- 상태 전이 정책의 중앙화와 사용자 수정 후 승인
- 3단계 Dashboard의 기한 임박·초과, 장기 대기, 직접 수정·완료·취소
- 최종 BC-01~BC-15 전체 회귀와 KPI 실측

위 항목은 삭제하거나 축소한 범위가 아니며 다음 구현 대상으로 유지한다.
