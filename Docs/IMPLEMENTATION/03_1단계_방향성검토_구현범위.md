# 03. 1단계 방향성검토 구현범위

## 1. 목적

초기 UI와 최소 Vertical Slice로 “Mail과 현재 Task 상태를 보고 Agent가 실제 Action을 결정·반영한다”는 방향을 검토한다. 완성형 E2E나 성능 평가 단계가 아니다.

이 문서는 1단계 목표 명세와 실제 검증 결과를 함께 관리한다. 완료 여부는 아래 완료 조건과 9절 실행 증적을 기준으로 판단한다.

## 2. 필수 시연 흐름

### 장면 A - 신규 Task

```text
합성 Mail 선택
-> M-01 회사 LLM API 분석
-> M-02 기존 후보 없음 확인
-> M-03 CREATE_TASK
-> Validation
-> M-04 SQLite Task/History 저장
-> M-05 Dashboard 표시
```

대표 Mail: “DDC 서버 패치 여부를 금요일까지 확인 부탁드립니다.”

### 장면 B - 후속 기한 변경

```text
동일 Thread 후속 Mail 선택
-> M-01 변경 의도·기한 분석
-> M-02 기존 TASK-001 매칭
-> M-03 UPDATE_TASK
-> Validation
-> M-04 기한 변경 및 전·후 History 저장
-> M-05 변경 결과 표시
```

대표 Mail: “금요일이 아니라 월요일까지 주셔도 됩니다.”

### 가능하면 장면 C - 불확실한 연결

관련 Task 후보가 복수인 Mail에서 `ASK_USER`와 후보 표시까지만 포함한다. 1단계 필수 완료 조건은 아니다.

## 3. 모듈별 1단계 범위

| 모듈 | 필수 구현 | 1단계 유예 |
|---|---|---|
| M-01 | JSON 로딩, Schema 정규화, 중복 확인, 회사 LLM 분석 | Gmail 입력, 복잡한 예외 |
| M-02 | `conversation_id` 우선 후보 검색, 단일 후보 Context | 의미 기반 복수 후보 고도화 |
| M-03 | `CREATE_TASK`, `UPDATE_TASK`; 가능하면 `ASK_USER` | 나머지 Action 완전 구현 |
| Validation | Enum, 필수값, Task ID, 날짜 형식 | 정교한 정책 설정 |
| M-04 | 최소 Mail/Task/History Table, Create/Update Transaction | 전체 상태·Link 기능 고도화 |
| M-05 | Mail 선택, 분석 결과, 현재 Task, Action/근거 표시 | 운영 Dashboard·고급 필터 |

## 4. 화면 최소 요구사항

- 테스트 Mail 선택 영역
- “Agent 분석” 실행 버튼
- 구조화된 Mail 분석 결과
- 선택 Action, 대상 Task, 신뢰도, 판단 근거
- 현재 Task 목록과 기한·상태
- 처리 전·후 값을 확인할 수 있는 간단한 History

UI 디자인보다 동작과 설명 가능성을 우선한다.

## 5. 권장 구현 순서

1. Action/Status/Mail/Task Schema
2. SQLite 초기 Schema와 Seed Task
3. M-04의 `CREATE_TASK`와 `UPDATE_TASK`
4. 회사 LLM API Client와 Mock Fallback
5. M-01 분석 및 Structured Output 검증
6. M-02 동일 Thread 매칭
7. M-03 Create/Update 결정
8. M-05 Streamlit 연결
9. 장면 A, B 수동 재현
10. 방향성 검토용 화면과 알려진 한계 정리

## 6. 1단계 완료 조건

- 로컬에서 Streamlit이 실행된다.
- 합성 Mail 장면 A와 B를 순서대로 선택할 수 있다.
- 회사 LLM API 응답이 검증된 구조로 표시된다.
- A에서 신규 Task가 생성되고 B에서 같은 Task의 기한이 변경된다.
- Task 변경과 History가 SQLite에 함께 저장된다.
- 화면에서 Action, 근거, 원본 Mail ID, 전·후 값을 확인할 수 있다.
- API 오류 또는 잘못된 JSON일 때 DB를 변경하지 않는다.

완료 여부는 실제 실행과 검증 후에만 체크한다.

## 7. 제외 범위

- 실제 Outlook/Microsoft Graph/n8n/사내 DB·서버
- 테스트 Gmail 연동
- `LINK_TO_TASK`, `SET_WAITING`, `MARK_COMPLETED`, `IGNORE`의 완전한 시연
- 10~15개 전체 Business Case와 KPI 실측
- RAG, Vector DB, Multi-Agent, LangGraph
- FastAPI, PostgreSQL, Redis, Docker, 배포 자동화

## 8. 방향성 검토 질문

1. 단순 Mail 분류가 아니라 State 기반 Agent Action으로 보이는가?
2. 신규 Task와 후속 변경 흐름이 사용자 문제를 해결하는가?
3. M-01~M-05의 책임이 과하거나 빠진 부분은 없는가?
4. `ASK_USER`가 필요한 기준이 적절한가?
5. 2단계에서 우선 확장할 Action과 상태 전이는 무엇인가?

## 9. 2026-08-25 구현 및 검증 증적

### 실제 구현

- 회사 LLM API Live 구조화 분석
- `MAIL-001` -> `CREATE_TASK` -> `TASK-001`, 기한 `2026-08-21`
- `MAIL-002` -> 동일 Conversation Task 매칭 -> `UPDATE_TASK`, 기한 `2026-08-24`
- SQLite Mail, Task, Link, History, Processing Result 저장
- 동일 `mail_id` 재입력 시 LLM과 DB 변경 재실행 방지
- M-01~M-05 단계별 Processing Event와 Streamlit 실행 로그 Tab
- 관련 후보 2개인 `MAIL-006`의 `ASK_USER`
- 사용자 선택: 기존 Task 연결, 신규 Task 생성, 무시
- Agent 제안과 사용자 최종 결정을 별도 History로 저장

### 실제 검증

- 1단계 Gate 당시 pytest 9건 통과, 3단계 확장 진행 후 전체 회귀 pytest 42건 통과
- CREATE/UPDATE 기존 회귀 통과
- ASK_USER 세 가지 사용자 선택 경로 통과
- API/Analyzer 실패 시 Task·History 미변경 및 실패 로그 저장 확인
- 동일 Mail 중복 시 LLM 재호출 없음 확인
- API Key, Authorization, Token 로그 마스킹 확인
- Streamlit 버튼 기반 CREATE 2건 -> ASK_USER -> 기존 Task 연결 시연 통과
- 회사 LLM API Live 기반 CREATE 2건 -> ASK_USER 후보 2개 -> 사용자 LINK_TO_TASK 통과
