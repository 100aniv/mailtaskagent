# 08. 멘토 시연 브리핑

## 1. 한 문장 소개

MailTaskAgent는 메일을 단순 요약하는 도구가 아니라, 새 메일과 기존 업무 상태를 함께 보고
다음 Action을 결정해 개인 업무의 생성·변경·대기·완료 Lifecycle을 관리하는 Agentic AI다.

## 2. 지금 어디까지 구현됐나

현재는 실제 Outlook 연결 직전의 **Core E2E**가 구현됐다.

- 회사 LLM API Live 분석
- 합성메일 15개 입력과 전체 자동 정리
- 고정 7 Action: `CREATE_TASK`, `UPDATE_TASK`, `LINK_TO_TASK`, `SET_WAITING`,
  `MARK_COMPLETED`, `ASK_USER`, `IGNORE`
- 5개 Task 상태: `TODO`, `IN_PROGRESS`, `WAITING_REPLY`, `COMPLETED`, `CANCELLED`
- 같은 Mail 대화 우선 매칭과 유사 Task 후보 점수·근거
- 완료·취소·기한 단축·모호한 판단의 사용자 확인
- SQLite Task·History·중복 방지
- 사용자의 Task 직접 수정·완료·취소와 전·후 History
- `오늘의 업무` 요약·우선순위·주의 항목, 메일 처리함·확인 필요·운영 로그·품질 검증 Dashboard
- 동일 Thread 선행 Mail과 선택 Task History Context 표시
- 완료·취소 Terminal 상태의 잘못된 재개 차단과 실패 Mail 재처리
- pytest `58 passed` (제품형 Dashboard 전체 Mail 처리·Gmail Adapter Contract·빈 상태 UI·History 및 로그 요약 회귀 포함)
- 회사 LLM Live 평가: 15/15 Case, 28/28 Action 단계 일치, 오류 0건

## 3. 왜 지금은 버튼을 누르나

지금 버튼은 **메일 도착을 재현하는 테스트 입력 장치**다. 메일을 한 건씩 분석해야만 하는
제품을 만든 것이 아니다.

```text
현재: 합성 JSON -> 전체 자동 정리 버튼 -> Agent Core -> Task/History
향후: Outlook/Graph -> 새 메일 자동 수집 -> 같은 Agent Core -> Task/History
```

현재도 `메일 처리함`의 `미처리 합성 메일 전체 자동 정리`를 한 번 누르면 Source에 있는
미처리 메일이 모두 처리된다. 실제 Outlook Adapter가 붙으면 새 메일 도착 또는 주기 수집이
이 버튼 역할을 대신한다. Outlook/Graph 연동은 Core 검증 후 Post-MVP 범위로 의도적으로
분리했다.

## 4. 4~5분 시연 순서

1. `업무 현황`의 `오늘의 업무`, 우선 처리 업무, 기한·대기 주의와 Agent 확인 필요 건을 보여준다.
2. `품질 검증` 탭에서 저장된 회사 LLM Live 결과 15/15와 Case별 비교표를 보여준다.
3. Sidebar의 `데모 DB 초기화`를 누른다.
4. `메일 처리함`에서 미처리 합성메일 전체 일괄 자동 정리를 설명한다. 시간이 부족하면 다음으로 간다.
5. `데모 도구`에서 `신규 업무 → 기한 변경`을 실행한다.
6. `업무 현황`에서 Task, 판단 Context와 변경 전·후 History를 보여준다.
7. `데모 도구`에서 `애매한 메일 → 사용자 확인`을 실행한다.
8. `확인 필요`에서 후보 점수·근거를 보고 기존 Task 연결·신규 생성·무시 중 하나를 선택한다.
9. `운영 로그`에서 Mail 입력, Schema 검증, LLM 호출, 후보 검색, Action 결정, DB 반영 시각과
   오류 위치를 보여준다.
10. `업무 현황`의 `Task 직접 수정 · 완료 · 취소`에서 사용자가 최종 통제권을 갖는다고 설명한다.

## 5. 멘토에게 말할 핵심

> 현재 Outlook 자체를 연결한 단계는 아니지만, Outlook이 전달할 Mail Schema 이후의
> Agent Core는 E2E로 연결했습니다. 회사 LLM Live로 15개 대표 시나리오를 격리 실행했고,
> 15개 모두와 28개 Action 단계가 기대값에 일치했습니다. 중요하거나 애매한 변경은 자동
> 반영하지 않고 사용자 확인으로 보내며, 모든 판단과 전·후 값은 History와 운영 로그에
> 남습니다.

## 6. 숫자를 설명할 때 주의할 점

- Live 시나리오 통과율: 15/15, 100%
- Live Action 단계 일치율: 28/28, 100%
- 자동 처리: 8/15, 53.3%
- 사용자 확인: 7/15, 46.7%
- 업무 요청 분류: 15/15, 100%
- 요청사항·기한 필수 필드: 26/26, 100%
- 단일 정답 Task 연결: 8/8, 100%
- 최신 Live 평가 총 시간: 76.554초
- 자동 테스트: 58 passed

사용자 확인 46.7%는 운영 자동화율 예측이 아니다. 완료·취소·기한 단축·후보 복수·모호한
날짜 같은 위험 Case를 의도적으로 많이 넣은 안전성 Dataset이기 때문이다. 위 정확도는 정의된
합성 Ground Truth에 한정되며, 실제 사람의 수동 정리시간 Baseline 비교는 아직 남았다고
솔직히 설명한다.

## 7. 광고·반복·일반 메일은 어떻게 되나

현재 업무 조치가 필요 없는 일반 공지와 Prompt Injection Mail은 `NON_TASK -> IGNORE`로
Task에서 제외된다. 광고·뉴스레터·자동 알림을 각각 별도 Category로 세분화하는 기능은 아직
명세에 넣지 않았다. 현재 Core는 “업무로 관리할지 여부”를 먼저 안전하게 구분하며, 세부
Mailbox Category는 Core를 깨뜨리지 않는 후속 분류 확장으로 검토한다.

## 8. UI는 최종인가

현재 UI는 기능 확인용 첫 화면을 벗어나 실제 사용 흐름 기준으로 재구성한 **Core 제품형
Dashboard**다. 첫 화면에서 오늘의 업무, 우선순위, 기한·대기 주의와 사용자 확인을 보고,
전체 메일 처리 결과, 사용자 확인, 로그, 품질 검증은 기능별 Tab에서 확인한다.
다만 Streamlit 기반 로컬 MVP이므로 시각 디자인과 운영용 인증·반응형 완성도까지 끝난
상용 UI는 아니다. Post-MVP에서 실제 Mail Source와 운영 환경이 정해지면 디자인을 한 번 더
다듬는다.

## 9. 남은 일과 범위 경계

Core 완성도를 위해 남은 항목:

- 수동 업무 정리 시간 대비 Agent 시간 측정
- 최종 Demo 영상과 수동 시간 실측의 AI Master 05~07 최종 동기화

Core 완료 후 선택적 고도화:

- 읽기 전용 Gmail Input Adapter Contract와 실제 OAuth 연결 완료
- `MailTaskAgent-Demo` Label의 비식별 합성 Mail 2건을 회사 LLM Live로 처리해
  `CREATE_TASK` → 동일 Thread `UPDATE_TASK`, 기한 변경과 실패 0건 확인

Post-MVP 사내 적용 항목:

- Outlook/Microsoft Graph 자동 수집
- n8n, 운영 알림, 인증·배포·다중 사용자

iCloud Mail은 현재 확정 범위가 아니다.
