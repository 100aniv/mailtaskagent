# 08. 멘토 시연 브리핑

## 1. 한 문장 소개

MailTaskAgent는 메일을 단순 요약하는 도구가 아니라, 새 메일과 기존 업무 상태를 함께 보고
다음 Action을 결정해 개인 업무의 생성·변경·대기·완료 Lifecycle을 관리하는 Agentic AI다.

## 2. 지금 어디까지 구현됐나

현재는 **AI Master Core E2E를 완료하고 읽기 전용 Gmail 개인 파일럿까지 검증한 상태**다.

- 회사 LLM API Live 분석
- 합성메일 15개 입력과 전체 자동 정리
- 고정 7 Action: `CREATE_TASK`, `UPDATE_TASK`, `LINK_TO_TASK`, `SET_WAITING`,
  `MARK_COMPLETED`, `ASK_USER`, `IGNORE`
- 5개 Task 상태: `TODO`, `IN_PROGRESS`, `WAITING_REPLY`, `COMPLETED`, `CANCELLED`
- 같은 Mail 대화 우선 매칭과 유사 Task 후보 점수·근거
- 완료·취소·기한 단축·모호한 판단의 사용자 확인
- SQLite Task·History·중복 방지
- 사용자의 Task 직접 수정·완료·취소와 전·후 History
- Gmail 연결 전 `실제 업무 모드`와 `MVP 시연 모드`, 연결 후 실제 업무 모드 자동 진입,
  동일 Agent Core와 분리된 실제/시연 DB
- `홈`, `내 업무`, `검토 요청`, `자동화 설정`, `운영 상태`, `설정`의 역할 기반 Dashboard
- 동일 Thread 선행 Mail과 선택 Task History Context 표시
- Task 연결 Gmail Thread의 수신·발신 후속 Mail 추적, 업무별 Mail 타임라인과 변경 이력
- 완료·취소 Terminal 상태의 잘못된 재개 차단과 실패 Mail 재처리
- pytest `122 passed` (Core, 제품형 Dashboard, Gmail Thread, 운영 자동화·복구, SQLite WAL·동시 동기화 단일 실행 잠금과 History UI 회귀 포함)
- 회사 LLM Live 평가: 15/15 Case, 28/28 Action 단계 일치, 오류 0건
- 별도 테스트 Gmail의 비식별 합성 Mail 20/20 수용시험, 재조회 중복 차단·실패 0건

## 3. 자동 처리는 어떻게 동작하나

실제 업무 모드에서는 Gmail 연결 후 Agent가 기본 1분 주기로 제한 Label의 신규 Mail과 이미
Task에 연결된 Thread의 수신·발신 후속 Mail을 자동 확인한다. 사용자는 메일마다 분석 버튼을
누르지 않으며, 필요할 때만 Agent를 일시정지한다.

```text
MVP 시연: 합성 JSON -> 전체 자동 정리 버튼 -> Agent Core -> Task/History
실제 파일럿: Gmail 1분 Polling -> 같은 Agent Core -> Task/History
향후 사내 적용: Outlook/Graph -> 같은 Agent Core -> Task/History
```

`미처리 합성 메일 전체 자동 정리` 버튼은 MVP 시연 모드에서 Mail 도착을 재현하기 위한
테스트 입력 장치다. 실제 Gmail 파일럿의 자동 Polling과 Windows Scheduler가 이 역할을 이미
대신하며, 향후 Outlook/Graph도 같은 M-01 Adapter 경계에 연결한다.

## 4. 4~5분 시연 순서

1. 첫 화면에서 `MVP 시연 모드`를 선택하고, 실제 운영 전환 시 시연 모드를 제거할 수 있음을 설명한다.
2. `품질 검증` 탭에서 저장된 회사 LLM Live 결과 15/15와 Case별 비교표를 보여준다.
3. Sidebar의 `데모 DB 초기화`를 누른다.
4. `메일 처리함`에서 미처리 합성메일 전체 일괄 자동 정리를 설명한다. 시간이 부족하면 다음으로 간다.
5. `데모 도구`에서 `신규 업무 → 기한 변경`을 실행한다.
6. `업무 현황`에서 Task, 판단 Context와 변경 전·후 History를 보여준다.
7. `데모 도구`에서 `애매한 메일 → 사용자 확인`을 실행한다.
8. `확인 필요`에서 후보 점수·근거를 보고 기존 Task 연결·신규 생성·무시 중 하나를 선택한다.
9. `운영 로그`에서 Mail 입력, Schema 검증, LLM 호출, 후보 검색, Action 결정, DB 반영 시각과
   오류 위치를 보여준다.
10. `업무 현황`의 `Task 직접 수정 · 완료 · 취소`에서 사용자가 최종 통제권을 갖는다고 설명한다.

## 5. 멘토에게 말할 핵심

> 현재 Outlook 자체를 연결한 단계는 아니지만, Outlook이 전달할 Mail Schema 이후의
> Agent Core는 E2E로 연결했습니다. 회사 LLM Live로 15개 대표 시나리오를 격리 실행했고,
> 15개 모두와 28개 Action 단계가 기대값에 일치했습니다. 중요하거나 애매한 변경은 자동
> 반영하지 않고 사용자 확인으로 보내며, 모든 판단과 전·후 값은 History와 운영 로그에
> 남습니다.

## 6. 숫자를 설명할 때 주의할 점

- Live 시나리오 통과율: 15/15, 100%
- Live Action 단계 일치율: 28/28, 100%
- 자동 처리: 8/15, 53.3%
- 사용자 확인: 7/15, 46.7%
- 업무 요청 분류: 15/15, 100%
- 요청사항·기한 필수 필드: 26/26, 100%
- 단일 정답 Task 연결: 8/8, 100%
- 최신 Live 평가 총 시간: 76.554초
- 자동 테스트: 122 passed
- Gmail 실메일 수용시험: 20/20 passed
- 외부 Mail 업무시간 Benchmark: 주 1.2~2.8시간 절감 잠재 시나리오

사용자 확인 46.7%는 운영 자동화율 예측이 아니다. 완료·취소·기한 단축·후보 복수·모호한
날짜 같은 위험 Case를 의도적으로 많이 넣은 안전성 Dataset이기 때문이다. 위 정확도는 정의된
합성 Ground Truth에 한정된다. 외부 Mail 업무시간 통계로 계산한 절감 잠재치는 프로젝트
실측값이 아니며, 실제 사람의 수동 정리시간 Baseline 비교는 후속 검증이라고 설명한다.

## 7. 광고·반복·일반 메일은 어떻게 되나

업무 조치가 필요 없는 일반 공지와 Prompt Injection Mail은 `NON_TASK -> IGNORE`로 Task에서
제외된다. 실제 업무 모드의 `자동화 설정`에서는 정확한 발신자 Email·Domain·제목 Keyword로
광고·뉴스레터·자동 알림 제외 Rule을 사용자가 관리할 수 있으며, 일치한 Mail은 LLM 호출 전에
`IGNORE` 근거를 남긴다.

## 8. UI는 최종인가

현재 UI는 사용자 Task 작업과 운영 모니터링을 분리한 **단일 사용자 제품형 Dashboard**다.
홈에서는 우선순위·검토 요청·최근 변경·최근 Mail만 확인하고, 내 업무에서 검색·상태 필터·
직접 생성·수정·완료·취소와 수신·발신 Mail 타임라인·변경 이력을 사용한다. 자동화 설정에는
중요도와 광고·반복 메일 제외 Rule, 실행 주기를 배치했다. 시연 전용 기능과 데이터는 별도
MVP 시연 모드로 격리했다. 다만 Streamlit 기반 로컬 단일 사용자 파일럿이므로 회사 표준
디자인 시스템, SSO·다중 사용자와 서버 반응형 운영은 사내 적용 단계다.

## 9. 남은 일과 범위 경계

최종 제출 패키지에서 남은 항목:

- 최종 Demo 영상·발표자료 확정과 리허설
- 실제 사용자 시간 측정은 필수 기능이 아니라 외부 Benchmark 기대효과를 보완하는 후속 검증

Core 완료 후 구현한 선택적 고도화:

- 읽기 전용 Gmail Input Adapter와 실제 OAuth 연결, 기본 1분 Polling·Windows Scheduler
- 별도 테스트 계정의 비식별 합성 Mail 20건 회사 LLM Live 수용시험 20/20
- Task 연결 Thread의 수신·발신 후속 Mail과 중복 차단, 업무별 Mail 타임라인·변경 이력

Post-MVP 사내 적용 항목:

- Outlook/Microsoft Graph 자동 수집
- n8n, 운영 알림, 인증·배포·다중 사용자

iCloud Mail은 현재 확정 범위가 아니다.
