# 05. 3단계 최종 E2E 구현범위

## 1. 목적

회사 제공 LLM API, M-01~M-05, SQLite, Streamlit을 통합하여 AI Master 최종 제출에 사용할 Core E2E를 완성하고 대표 Business Case, KPI, 최종 Demo로 검증한다.

실제 Outlook·Microsoft Graph·n8n 연동 없이도 합성·비식별 Dataset으로 3단계 완료가 가능해야 한다.

현재 이 문서는 목표 명세이며 구현 완료나 KPI 달성을 선언하지 않는다.

## 2. 최종 E2E 경계

```text
합성 Mail Dataset 또는 선택적 테스트 Gmail
-> M-01 Mail Input & Analyzer
-> M-02 Task Context Matcher
-> M-03 Agent Action Decision
-> Pydantic/정책 Validation
-> M-05 User Review when needed
-> M-04 Task/Link/History Transaction
-> M-05 Streamlit Dashboard
-> Test Runner와 KPI 집계
```

## 3. 필수 기능

### Agent Core

- 7 Action 전체 실행 경로
- 5 Task 상태와 허용 상태 전이
- Metadata 우선, 정확도 미달이 확인될 때만 제한적 LLM 의미 매칭 검토
- 구조화 출력 검증과 오류/재시도
- Human-in-the-loop 승인·수정·거절
- 사용자 확정값 우선과 중복 처리 방지

### 데이터와 이력

- Mail, Task, Mail-Task Link, History, Processing Result
- 변경 전·후, 근거 Mail, Action, 이유, 신뢰도, 사용자 결정, 시각
- Task 변경과 History의 Transaction 일관성
- 테스트 반복을 위한 DB 초기화/Seed 절차

### Dashboard

- 합성 Mail 선택·처리
- 분석 결과와 Action 근거
- TODO/진행/회신 대기/완료/취소 Task 조회
- 기한 임박·초과, 장기 대기 표시
- 확인 대기 Queue와 사용자 결정
- Task 직접 수정·완료·취소
- Mail 연결 및 변경 History 조회
- 오류와 재처리 상태

## 4. 최종 Business Case

`06_테스트_전략_및_케이스.md`의 대표 10~15개 Case를 기준으로 한다. 필수 범주는 다음과 같다.

- 신규 요청과 `CREATE_TASK`
- 후속 Mail의 `UPDATE_TASK`와 `LINK_TO_TASK`
- 발신 Mail의 `SET_WAITING`과 자료 도착 후 재개
- 명확/모호한 완료
- 복수 후보·모호한 날짜의 `ASK_USER`
- 일반 공지의 `IGNORE`
- 취소와 동일 Mail 중복 처리
- LLM/Schema/DB 오류의 안전한 실패

## 5. KPI 계획

공식 문제 정의의 목표를 그대로 사용한다.

| KPI | 목표 | 3단계 산출물 |
|---|---:|---|
| 업무 요청 Mail 분류 정확도 | 90% 이상 | Case별 정답/예측과 계산식 |
| 요청사항·기한 추출 정확도 | 90% 이상 | 필드별 평가 결과 |
| 신규/기존 Task 연결 정확도 | 85% 이상 | 기대/예측 Task ID |
| Task 상태 변경 판단 정확도 | 85% 이상 | 기대/예측 Action·State |
| E2E 시나리오 성공률 | 90% 이상 | Case별 단계 통과표 |
| 업무 정리 소요시간 | 30% 이상 단축 목표 | 수동/Agent 측정 절차와 결과 |

목표 미달을 숨기지 않는다. 실측값, 실패 원인, 개선 전·후를 구분해 기록한다.

## 6. 품질·안전 요구사항

- 근거 없는 Task, 기한, 요청자, 완료 상태를 생성하지 않는다.
- `ASK_USER` 대상은 사용자 결정 전 중요 변경을 수행하지 않는다.
- Mail 본문을 시스템 명령으로 실행하지 않는다.
- 전체 Mailbox가 아닌 필요한 Mail/Task Context만 LLM에 전달한다.
- API Key와 민감정보를 코드·화면·로그에 노출하지 않는다.
- LLM 장애 시 DB 변경 없이 오류를 표시하고 Mock은 Demo 대체임을 명확히 표시한다.

## 7. 최종 Demo 시나리오

1. 초기 Dashboard와 합성 Dataset을 보여준다.
2. SC-001 신규 Mail로 Task를 생성한다.
3. SC-002 후속 Mail로 기한을 변경한다.
4. 발신 Mail로 회신 대기 상태를 설정하고 자료 도착으로 업무를 재개한다.
5. SC-003 복수 후보에서 `ASK_USER`와 사용자 선택을 보여준다.
6. 일반 공지가 `IGNORE`되는 것을 보여준다.
7. 완료 제안과 승인 후 History를 보여준다.
8. 테스트 요약과 KPI 실측값, 실패 Case, 한계를 설명한다.

## 8. 최종 완료 조건

- 로컬 환경에서 설치·초기화·실행 절차가 재현된다.
- M-01~M-05와 7 Action이 하나의 E2E에서 연결된다.
- SC-001/002/003와 대표 Case가 실제 테스트된다.
- 사용자 검토와 History 추적이 동작한다.
- KPI가 정의된 계산 방식으로 실제 측정된다.
- 실패 Case와 알려진 한계가 기록된다.
- Demo 화면/영상과 공식 05~07 문서에 옮길 증적이 준비된다.

## 9. 3단계 제외 범위

- 실제 개인/조직 Outlook Mailbox
- Microsoft Graph App Registration과 운영 권한
- n8n Mail Polling·Reminder
- 사내 DB·서버·Container·SSO·다중 사용자
- Slack/Teams 운영 알림
- RAG, Vector DB, Multi-Agent, LangGraph의 필수 도입

이 항목들은 4단계 Post-MVP에서 별도 검토한다.
