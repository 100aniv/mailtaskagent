# 05. 3단계 최종 E2E 구현범위

## 1. 목적

회사 제공 LLM API, M-01~M-05, SQLite, Streamlit을 통합하여 AI Master 최종 제출에 사용할 Core E2E를 완성하고 대표 Business Case, KPI, 최종 Demo로 검증한다.

실제 Outlook·Microsoft Graph·n8n 연동 없이도 합성·비식별 Dataset으로 3단계 완료가 가능해야 한다.

현재 이 문서는 목표 명세와 실제 완료 증적을 함께 관리하며, 측정하지 않은 KPI만 달성값으로 선언하지 않는다.

2026-09-02 회사 LLM Live, M-01~M-05, Gmail 파일럿, 경량 Task Context Agentic RAG와
제한적 ReAct 재판단을 최종 MVP로 구현했다. 신규·전체 회귀는 `136 passed`, Task Context
Agent 회사 LLM Live 합성 검증은 3/3이며 별도 Evidence를 생성했다.

## 2. 최종 E2E 경계

```text
합성 Mail Dataset 또는 선택적 테스트 Gmail
-> M-01 Mail Input & Analyzer
-> M-02 동일 Thread 우선 / Task Context Retrieval
-> M-03 Task Context Agent 판단 / 최대 1회 Query Rewrite
-> Python M-03 Agent Action Decision
-> Pydantic/정책 Validation
-> M-05 User Review when needed
-> M-04 Task/Link/History Transaction
-> M-05 Streamlit Dashboard
-> Test Runner와 KPI 집계
```

## 3. 필수 기능

### Agent Core

- 7 Action 전체 실행 경로
- 5 Task 상태와 허용 상태 전이
- 동일 `conversation_id`의 단일 활성 Task는 결정론적으로 우선 연결
- 동일 Thread로 확정할 수 없을 때 SQLite Task·Mail·History top-k를 사용하는 경량 Task Context RAG
- 별도 Task Context Agent의 관계 판단과 최대 1회 Query Rewrite, 실패 시 `ASK_USER`
- LLM Action은 제안값이며 Python M-03과 기존 Validation을 최종 Guard로 유지
- 구조화 출력 검증과 오류/재시도
- Human-in-the-loop 승인·수정·거절
- 사용자 확정값 우선과 중복 처리 방지

### 데이터와 이력

- Mail, Task, Mail-Task Link, History, Processing Result
- 변경 전·후, 근거 Mail, Action, 이유, 신뢰도, 사용자 결정, 시각
- Task 변경과 History의 Transaction 일관성
- 테스트 반복을 위한 DB 초기화/Seed 절차

### Dashboard

- 첫 화면에서 `실제 업무 모드`와 `MVP 시연 모드` 선택
- 동일 Agent Core 공유, 실제 업무 DB와 시연 DB 분리
- 실제 업무 모드에는 업무 현황·메일 처리함·확인 필요·운영 로그만 노출
- MVP 시연 모드에는 품질 검증·데모 도구 추가 노출
- 합성 Mail 선택·처리
- 분석 결과와 Action 근거
- TODO/진행/회신 대기/완료/취소 Task 조회
- 기한 임박·초과, 장기 대기 표시
- 확인 대기 Queue와 사용자 결정
- Task 직접 수정·완료·취소
- Mail 연결 및 변경 History 조회
- 오류와 재처리 상태

## 4. 최종 Business Case

`06_테스트_전략_및_케이스.md`의 대표 10~15개 Case를 기준으로 한다. 필수 범주는 다음과 같다.

- 신규 요청과 `CREATE_TASK`
- 후속 Mail의 `UPDATE_TASK`와 `LINK_TO_TASK`
- 발신 Mail의 `SET_WAITING`과 자료 도착 후 재개
- 명확/모호한 완료
- 복수 후보·모호한 날짜의 `ASK_USER`
- 일반 공지의 `IGNORE`
- 취소와 동일 Mail 중복 처리
- LLM/Schema/DB 오류의 안전한 실패
- 다른 `conversation_id`·다른 표현의 동일 Task 연결, 저신뢰 Query Rewrite 성공과 재판단 후 `ASK_USER`
- 후보 밖 Task ID·RAG API 실패 시 DB 무변경, 기존 중요 변경 승인 Gate 유지

## 5. KPI 계획

공식 문제 정의의 목표를 그대로 사용한다.

| KPI | 목표 | 3단계 산출물 |
|---|---:|---|
| 업무 요청 Mail 분류 정확도 | 90% 이상 | Case별 정답/예측과 계산식 |
| 요청사항·기한 추출 정확도 | 90% 이상 | 필드별 평가 결과 |
| 신규/기존 Task 연결 정확도 | 85% 이상 | 기대/예측 Task ID |
| Task 상태 변경 판단 정확도 | 85% 이상 | 기대/예측 Action·State |
| E2E 시나리오 성공률 | 90% 이상 | Case별 단계 통과표 |
| 업무 정리 소요시간 | 30% 이상 단축 목표 | 외부 Benchmark 기대효과 계산, 실제 사용자 실측은 후속 검증 |

목표 미달을 숨기지 않는다. 실측값, 실패 원인, 개선 전·후를 구분해 기록한다.

## 6. 품질·안전 요구사항

- 근거 없는 Task, 기한, 요청자, 완료 상태를 생성하지 않는다.
- `ASK_USER` 대상은 사용자 결정 전 중요 변경을 수행하지 않는다.
- Mail 본문을 시스템 명령으로 실행하지 않는다.
- 전체 Mailbox가 아닌 필요한 Mail/Task Context만 LLM에 전달한다.
- API Key와 민감정보를 코드·화면·로그에 노출하지 않는다.
- LLM 장애 시 DB 변경 없이 오류를 표시하고 Mock은 Demo 대체임을 명확히 표시한다.

## 8. 최종 완료 조건

- 로컬 환경에서 설치·초기화·실행 절차가 재현된다.

- SC-001/002/003와 대표 Case가 실제 테스트된다.

- 정확도 KPI는 정의된 계산 방식으로 실제 측정되고, 시간 KPI는 외부 Benchmark 추정과 프로젝트 실측 여부를 구분한다.
- Task Context RAG 신규 테스트와 기존 전체 pytest가 모두 통과하고 별도 Evidence가 생성된다.
- 실패 Case와 알려진 한계가 기록된다.
- Demo 화면/영상과 공식 05~07 문서에 옮길 증적이 준비된다.
