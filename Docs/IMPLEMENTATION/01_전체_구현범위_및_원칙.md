# 01. 전체 구현범위 및 원칙

## 1. 문서 목적과 기준

이 폴더는 MailTaskAgent의 실제 개발을 위한 내부 명세다. 구현의 기준은 `../AI_MASTER/`의 공식 산출물이며, 공식 문서와 충돌하면 공식 문서를 우선한다.

이 문서의 기능, 테스트, KPI는 전체 목표와 완료 조건이다. 실제 구현·검증 증적은
`03_1단계_방향성검토_구현범위.md`, `04_2단계_중간시연_구현범위.md`,
`06_테스트_전략_및_케이스.md`에 구분해 기록한다. 증적이 없는 목표는 구현 완료 또는
실측 완료로 간주하지 않으며, 검증된 결과만 AI Master 공식 05~07 문서에 옮긴다.

## 2. 제품 정의

MailTaskAgent는 Mail을 단순 요약하는 도구가 아니다. 현재 Mail, 선행·후행 Mail, Task 상태와 변경 이력을 함께 분석하여 다음 Action을 결정하고, 검증과 사용자 확인을 거쳐 Task Lifecycle을 관리하는 개인 업무관리 Agent다.

```text
Mail Input
-> M-01 분석
-> M-02 Task Context 매칭
-> M-03 Action 결정
-> 출력 검증
-> M-04 Task/History 반영 또는 M-05 사용자 확인
-> M-05 Dashboard 표시
```

## 3. 고정 Agent Action

Action 이름은 아래 7개로 고정하며 임의로 추가·변경하지 않는다.

| Action | 의미 | 실행 원칙 |
|---|---|---|
| `CREATE_TASK` | 신규 업무 생성 | 기존 Task 후보가 없고 신규 요청이 명확할 때 |
| `UPDATE_TASK` | 기존 Task의 요청사항·기한·상태 변경 | 대상 Task와 변경 근거가 명확할 때 |
| `LINK_TO_TASK` | Mail을 기존 Task에 연결 | 관련성은 명확하지만 Task 필드 변경이 없을 때 |
| `SET_WAITING` | 회신·추가 정보 대기 상태 설정 | 발신 Mail 또는 사용자 결정으로 대기 전환할 때 |
| `MARK_COMPLETED` | 완료 처리 제안 | 완료 근거가 명확하고 승인 정책을 통과할 때 |
| `ASK_USER` | 사용자에게 판단 요청 | 후보 복수, 낮은 신뢰도, 모호한 기한·완료·취소일 때 |
| `IGNORE` | 업무관리 대상에서 제외 | 업무 요청이나 Task 변화가 아닐 때 |

Task 상태는 공식 설계에 따라 `TODO`, `IN_PROGRESS`, `WAITING_REPLY`, `COMPLETED`, `CANCELLED`를 사용한다. 취소는 별도 Agent Action을 추가하지 않고 검증된 `UPDATE_TASK` 또는 사용자 결정으로 상태를 변경한다.

## 4. 핵심 공통 모듈

시나리오별 코드를 중복 작성하지 않고 다음 M-01~M-05를 모든 단계에서 확장한다.

| 모듈 | 이름 | 책임 |
|---|---|---|
| M-01 | Mail Input & Analyzer | 입력 정규화, 중복 확인, 업무 요청과 주요 정보 추출 |
| M-02 | Task Context Matcher | Task·Thread·History 조회와 관련 Task 후보 탐색 |
| M-03 | Agent Action Decision | 현재 Mail Context와 Task 상태에 따른 단일 Action 결정 |
| M-04 | Task State & History Manager | Task 생성·변경·연결·상태 전이와 감사 이력 저장 |
| M-05 | User Review & Dashboard | 결과 표시, 승인·수정·거절, 업무현황과 이력 조회 |

Pydantic/JSON Schema 기반 Action Validation은 M-03과 M-04 사이의 공통 Guard로 둔다.

## 5. 기술 및 환경 원칙

- 언어·Workflow: Python 함수와 State 객체 기반 단일 Agent
- LLM: 회사 제공 LLM API
- 저장: SQLite
- UI: Streamlit
- 검증: Pydantic 또는 JSON Schema
- 테스트: pytest와 합성·비식별 Mail Dataset
- 실행: 로컬 Windows 환경, `venv`, `localhost`
- 기본 입력: 합성·비식별 JSON Dataset
- 선택 입력: 테스트 전용 Gmail과 합성 Mail
- Secret: 환경 변수로 분리하고 저장소에 커밋하지 않음

2026-08-27 기준 읽기 전용 테스트 Gmail Adapter Contract와 합성 API Payload 검증을
Core와 분리해 구현했다. 실제 OAuth 계정 연결 후 제한 Label의 비식별 합성 Mail 2건을
회사 LLM Live로 처리해 `CREATE_TASK`와 동일 Thread `UPDATE_TASK`, 실패 0건을 확인했다.

RAG, Vector DB, Multi-Agent, LangGraph는 현재 필수 기술이 아니다. FastAPI, PostgreSQL, Redis, Docker 등도 해결해야 할 실제 요구가 생기기 전에는 추가하지 않는다.

## 6. LLM과 Application Logic의 경계

### LLM이 담당하는 것

- 자연어 Mail의 업무 요청·기한·요청자·변경 의도 추출
- Mail 의미와 Intent, 판단 근거·신뢰도의 구조화
- Task 또는 Task ID를 생성하거나 DB를 직접 변경하지 않음

### Application Logic이 담당하는 것

- Schema, Enum, 날짜, 필수값, Task ID, 상태 전이 검증
- 중복 Mail 방지, Metadata·Token 기반 M-02 후보 검색
- 현재 Mail Context와 Task 상태를 이용한 Python M-03 최종 Action 결정
- SQLite Transaction과 History 저장
- 사용자 승인 정책과 실제 Task 변경
- 오류·재시도·로그 관리

LLM은 DB를 직접 변경하지 않는다. 검증에 실패한 결과는 실행하지 않는다.

## 7. 구현 단계

| 단계 | 목적 | 필수 결과 | 제외/유예 |
|---|---|---|---|
| 1단계 방향성 검토 | 초기 UI와 핵심 Vertical Slice 검증 | 합성 Mail, 회사 LLM API, `CREATE_TASK`, `UPDATE_TASK`, SQLite, Streamlit | 외부 Mail·운영 연동, 전체 고도화 |
| 2단계 중간 시연 | M-01~M-05와 주요 Action 동작 검토 | SC-001/002/003, 주요 상태 전이, 사용자 확인, History | KPI 확정, 사내 운영환경 |
| 3단계 최종 E2E | 전체 핵심 기능·테스트·Demo 완성 | 7 Action, 5 상태, 10~15 Business Case, KPI 측정 | Outlook/Graph/n8n 필수화 |
| 4단계 Post-MVP | 실전 개인 사용 검증 후 사내 서비스 확장 | Gmail 실전 UX·사용자 Priority Rule → Outlook/Graph·사내 운영환경 | AI Master Core 완료 조건과 분리 |

## 8. 권장 개발 순서

1. 공통 Enum과 Pydantic Schema를 확정한다.
2. SQLite의 Mail, Task, Mail-Task Link, History 저장 구조를 만든다.
3. M-01의 JSON 입력·중복 확인·회사 LLM 분석을 구현한다.
4. M-04의 결정론적 Task 저장과 History Transaction을 먼저 검증한다.
5. M-02의 Metadata·Token 기반 후보 검색을 구현하고, 실측 정확도가 목표에 미달할 때만 의미 비교를 제한적으로 검토한다.
6. M-03의 Action 결정과 Validation을 구현한다.
7. M-05의 최소 Streamlit UI로 입력·판단·Task·History를 연결한다.
8. 단계별 Business Case를 통과시킨 뒤 다음 단계로 확장한다.

### Post-MVP 실전 개발 순서

1. `ai-master-mvp-v1` Git Tag의 3단계 제출용 MVP를 변경하지 않는 복구 기준으로 유지한다.
2. 테스트 Gmail과 별도 실제 업무 DB에서 사용자 중심 UI, Task 직접 관리와 중요도·긴급도 규칙을 검증한다.
3. 우선순위는 기한·회신 대기 같은 긴급도와 고객사·연락처·키워드·사용자 직접 지정 중요도를 분리해 계산한다.
4. 결정 가능한 사용자 설정은 Python Rule로 처리하고, 어떤 규칙이 적용됐는지 근거를 저장·표시한다.
5. 사용자가 등록한 정확한 발신자·Domain·제목 Keyword 제외 Rule은 새 Mail의 M-01 분석 전에
   적용하고 기존 `IGNORE` Action과 적용 근거를 저장한다. 본문 Keyword만으로 자동 제외하지 않는다.
6. RAG는 고객사 SLA·사내 절차·업무 매뉴얼처럼 검색할 실제 문서 Corpus와 요구가 생길 때만 추가한다.
7. Gmail에서 실전 Workflow와 안전성이 확인된 뒤 동일 M-01 Adapter 경계로 Outlook/Microsoft Graph를 연결한다.
8. Outlook 전 Gmail Gate는 실제 제한 Label Live 동기화뿐 아니라 Gmail API 형식으로 변환한
   전체 Business/Security Case의 Adapter→Agent Core 회귀까지 통과해야 한다.
   이어서 별도 송신 계정과 테스트 Inbox로 비식별 실메일 20건을 송수신하여 Thread,
   INBOUND/OUTBOUND, 7 Action, 사용자 확인, Priority·제외 기준과 재조회 중복 방지를 검증한다.
9. 로컬 Gmail 20건 Gate를 통과한 뒤에만 Post-MVP 단일 사용자 VM/Application Server를
   구성한다. 서버에서는 같은 20건 회귀, Scheduler 상시 실행, 재시작 복구, Health Check와
   Backup을 다시 검증하고, 그 결과가 확인된 뒤 Outlook/Microsoft Graph Live로 이동한다.
10. 사내 운영 알림 채널은 Slack으로 고정한다. 초기에는 Incoming Webhook으로 실패·검토 필요
   건수만 알리고 Mail 원문, Task 제목, 사용자 정보와 Secret은 전송하지 않는다.
11. 실제 업무 Navigation은 `홈`, `내 업무`, `검토 요청`, `자동 분류`, `운영 상태`, `설정`으로
    구성한다. 사용자의 Task 처리 화면과 Gmail 배치·Mail 처리 내역·Agent 단계 로그를 보는
    운영 모니터링 화면을 분리한다. VIP·고객사·중요 키워드와 광고·반복 메일 제외는
    `자동 분류`에서 바로 찾게 하고, 연결·알림·백업은 `설정`에 배치한다.
12. `홈`은 우선순위 업무·검토 요청·최근 변경·최근 Mail 3건만 보여준다. Agent 실행 여부,
    Gmail 연결, 마지막 확인 시각과 실패 건수는 홈 상단의 얇은 운영 상태 바로 분리한다.
    Gmail Push 수신이 아니므로 실시간이라는 표현을 사용하지 않고 갱신 기준을 화면에 안내한다.
13. Gmail OAuth 연결 후 실제 업무 모드로 바로 진입하고 Agent는 기본 1분 Polling 상태로
    실행한다. 사용자는 기능을 활성화하는 대신 필요할 때만 사이드바에서 일시정지·재실행한다.
    수동 동기화 버튼은 핵심 사용 흐름에서 제거하고 장애 점검 수단으로만 유지한다.
14. 제한 Gmail Label은 신규 업무가 Agent에 들어오는 안전한 유입 관문으로 유지한다. 한 번
    Task가 생성·연결된 Gmail `threadId`는 SQLite의 `conversation_id`를 기준으로 별도 추적해,
    이후 라벨 상속 여부와 관계없이 같은 Thread의 Inbox·Sent Mail을 함께 수집한다. 보낸편지함
    전체를 무차별 분석하지 않으며 최대 100개 연결 Thread만 읽기 전용으로 추적한다. 삭제되어
    404/410인 연결 Thread는 건너뛰되 인증·권한·네트워크 오류는 숨기지 않고 실행 실패로 남긴다.
15. 실제 업무 화면은 저장된 Task·Mail을 SQLite에서 먼저 표시해 Gmail 네트워크 조회로 첫 화면을
    막지 않는다. 신규 사용자처럼 운영 DB가 비어 있을 때만 최초 Gmail 조회를 수행하고, 이후
    갱신은 화면 Fragment 또는 외부 Scheduler의 동일 1회 동기화 계약이 담당한다.

## 9. 공통 완료 원칙

- 실행한 기능만 완료로 표시한다.
- 테스트를 실제로 실행하기 전에는 통과·정확도 수치를 기록하지 않는다.
- 각 변경은 원본 `mail_id`, Action, 근거, 전·후 값, 시각, 사용자 결정을 추적할 수 있어야 한다.
- 모호한 판단은 임의 확정하지 않고 `ASK_USER` 또는 보류 상태로 남긴다.
- 기능을 추가할 때 M-01~M-05 중 책임 위치를 먼저 결정한다.
- Post-MVP 연동 실패가 3단계 Core E2E의 완료를 막지 않도록 Adapter 경계를 유지한다.
