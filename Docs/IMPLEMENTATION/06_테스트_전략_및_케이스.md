# 06. 테스트 전략 및 케이스

## 1. 목적과 현재 상태

과도한 Case 수보다 실제 업무 흐름을 대표하는 10~15개 Business Case로 분류, 추출, Task 연결, Action, 상태 전이, 사용자 확인, History를 검증한다.

아래 내용은 전체 단계의 테스트 계획이다. 현재 자동·Live·UI 실행 증적은 9절에 기록한다.
3단계 대표 15개 E2E Case, Action 단계와 분류·필드 추출·Task ID 단위 세부 KPI는
Live 실측을 완료했다. 수동 대비 시간 KPI만 아직 완료로 간주하지 않는다.

## 2. 테스트 데이터 구조

- 입력: 합성·비식별 Mail Dataset
- 정답: 입력과 분리한 기대 Action, Task ID, 필드, 상태, Review 필요 여부
- 한 Case: 1~3개 Mail과 필요 시 초기 Task/History
- 실제 개인정보·사내 서버명·내부 내용 사용 금지
- 테스트 Gmail 사용 시에도 동일한 합성 Mail만 사용

## 3. 테스트 계층

| 계층 | 대상 | LLM 사용 | 목적 |
|---|---|---|---|
| Unit | Schema, 날짜, 중복, 상태 전이, DB 함수 | Mock | 결정론적 로직 검증 |
| Contract | 회사 LLM API Client, Structured Output | 실제/Stub 분리 | 응답 형식·오류 처리 |
| Integration | M-01~M-04, M-05 Review | Mock 우선 | 모듈 경계·Transaction |
| Business E2E | Mail 입력부터 Dashboard/DB | 실제 회사 LLM API | 사용자 시나리오와 KPI |
| Regression | 고정 Dataset 전체 | 설정된 모델 | Prompt·모델 변경 영향 |

LLM 결과의 변동성과 Application Logic 오류를 구분할 수 있도록 Mock 테스트와 실제 API 평가를 분리한다.

## 4. 대표 Business Case 15개

| ID | 연계 시나리오 | 초기 조건·입력 | 기대 Action/결과 | 핵심 검증 |
|---|---|---|---|---|
| BC-01 | SC-001 | 신규 업무, 명확한 기한 | `CREATE_TASK`, `TODO` | 요청·기한·근거 저장 |
| BC-02 | SC-001 | 신규 업무, 기한 없음 | `CREATE_TASK` 또는 정책상 Review | 존재하지 않는 기한 생성 금지 |
| BC-03 | SC-001 | 일반 공지, 조치 불필요 | `IGNORE` | Task 미생성, 처리 이력 |
| BC-04 | SC-002 | 동일 Thread의 기한 연장 | `UPDATE_TASK` | 동일 Task, 전·후 기한 |
| BC-05 | SC-002 | 동일 Thread의 기한 단축 | `UPDATE_TASK` + 필요 시 Review | 중요 변경 검증 |
| BC-06 | SC-002 | 기존 업무의 추가 요청 | `UPDATE_TASK` 또는 `LINK_TO_TASK` | 변경 여부에 따른 Action 구분 |
| BC-07 | SC-002 | 사용자가 자료 요청 Mail 발신 | `SET_WAITING`, `WAITING_REPLY` | 방향, `waiting_since` |
| BC-08 | SC-002 | 대기 중 자료 수신 | `UPDATE_TASK`, `IN_PROGRESS` | 기존 Task 연결·대기 해제 |
| BC-09 | SC-002 | 명확한 완료 근거 | `MARK_COMPLETED` 제안/승인 | 승인 정책·완료 History |
| BC-10 | SC-003 | 완료인지 불분명한 표현 | `ASK_USER` | 자동 완료 0건 |
| BC-11 | SC-003 | 관련 Task 후보 2개 | `ASK_USER` | 후보·근거·사용자 선택 |
| BC-12 | SC-003 | 다른 Thread의 유사 업무 | 매칭 또는 `ASK_USER` | Metadata와 의미 판단 경계 |
| BC-13 | SC-003 | “다음 주 중” 등 모호한 기한 | `ASK_USER` 또는 기한 미확정 | 임의 날짜 금지 |
| BC-14 | SC-002/003 | 취소 요청 | 사용자 확인 후 `CANCELLED` | 별도 Action 추가 금지, 이력 |
| BC-15 | 공통 | 동일 `mail_id` 재입력 | 기존 처리 결과 반환 | 중복 Task·History 0건 |

BC-02와 BC-06은 정책과 문맥에 따라 허용 결과가 둘일 수 있으므로 정답 Dataset에 판정 조건을 명시한다. 모호한 기대값을 테스트 코드에 숨기지 않는다.

## 5. 공통 예외·안전 검증

대표 15개 Case에 아래 검증을 필요한 곳에 결합하며 별도 대규모 Case로 늘리지 않는다.

- 회사 LLM API Timeout/인증 실패: DB 변경 없음, 오류 표시
- 잘못된 JSON/Schema: 최대 1회 재시도 후 실패 또는 Review
- 존재하지 않는 Task ID: 실행 차단
- DB Transaction 실패: Task/Link/History 모두 Rollback
- Mail 본문의 Prompt Injection 문구: 시스템 명령으로 실행하지 않음
- 일부 Case 실패: 나머지 Case 실행 가능
- Secret·민감 원문: 로그 노출 금지

## 6. KPI 계산

| KPI | 계산 방법 | 목표 |
|---|---|---:|
| 업무 요청 분류 정확도 | 올바른 업무/비업무 판정 ÷ 전체 분류 대상 | 90% 이상 |
| 주요 정보 추출 정확도 | 정답과 일치한 필수 필드 ÷ 전체 필수 필드 | 90% 이상 |
| Task 연결 정확도 | 기대 Task ID와 일치한 연결 ÷ 연결 대상 Case | 85% 이상 |
| 상태 변경 판단 정확도 | 기대 Action·State와 일치한 수 ÷ 상태 변경 Case | 85% 이상 |
| E2E 성공률 | 모든 필수 단계가 성공한 Case ÷ 전체 E2E Case | 90% 이상 |
| 업무 정리시간 단축률 | `(수동 시간-Agent 시간) / 수동 시간 × 100` | 30% 이상 |

소수 Case에서는 한 건의 영향이 크므로 분자/분모와 실패 Case ID를 함께 공개한다. 목표 미달도 실제 결과로 기록한다.

## 7. 단계별 테스트 범위

- 1단계: BC-01, BC-04와 LLM/DB 안전 실패
- 2단계: BC-01~BC-13 중 대표 7~9개
- 3단계: BC-01~BC-15 전체와 KPI 측정
- 4단계: Graph/n8n/사내 DB 계약·권한·운영 테스트 추가

## 8. 실행 증적 템플릿

실제 실행 후 Case마다 다음을 남긴다.

```text
Case ID:
실행 일시 / 모델 설정 / Prompt 버전:
입력 Mail ID:
초기 Task 상태:
기대 Action / 실제 Action:
기대 Task·필드·상태 / 실제 결과:
사용자 Review 여부:
DB/History 확인:
통과 여부:
실패 원인 및 후속 조치:
```

“테스트 완료”, “정확도 달성”은 이 증적과 자동 테스트 결과가 존재할 때만 사용한다.
