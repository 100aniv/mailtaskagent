# 2026-09-02 MailTaskAgent 멘토 시연 이해자료 및 스크립트

## 1. 내일 반드시 기억할 결론

MailTaskAgent는 메일을 요약하는 프로그램이 아니다. 메일이 새 업무인지, 기존 업무의 변경인지,
회신을 기다려야 하는지, 완료 후보인지 판단하여 Task의 상태와 이력을 계속 관리하는 Agent다.

현재 상태는 다음 세 줄로 설명한다.

1. 회사 LLM, M-01~M-05, 7 Action, 5 Status, 사용자 확인, DB, Dashboard와 Gmail 파일럿까지
   연결된 **시연 가능한 Core E2E 기준선**은 검증했다.
2. 다른 Thread·다른 표현의 동일 업무를 더 깊게 판단하는 **Task Context RAG는 멘토 피드백을
   반영한 최종 MVP 잔여 과제**이며 아직 구현하지 않았다.
3. Outlook·사내 인증·서버·운영 DB와 사내 문서 RAG는 **최종 MVP 이후 Post-MVP**다.

따라서 내일 “최종 MVP가 모두 끝났다”고 말하지 않는다. 대신 “작동하는 기준선을 먼저
완성·검증했고, 멘토 피드백을 최종 MVP의 남은 설계로 정확히 반영했다”고 말한다.

## 2. 초보자 관점의 전체 구조

```text
메일이 들어옴
  ↓
M-01: 이 메일이 무슨 뜻인지 LLM이 구조화
  ↓
M-02: 새 업무인지, 연결할 기존 Task가 있는지 검색
  ↓
M-03: 7개 Action 중 다음 행동을 Python 정책이 결정
  ↓
Validation: 잘못된 ID·날짜·상태 변경인지 검사
  ↓
안전하면 DB 반영 / 애매하거나 중요하면 사용자에게 확인
  ↓
M-04: Task·Mail 연결·변경 전후 History 저장
  ↓
M-05: Dashboard에서 업무·검토 요청·로그 표시
```

각 기술의 역할은 다음과 같다.

| 구성 | 쉬운 설명 | 실제 책임 |
|---|---|---|
| 회사 LLM `gpt-4.1-mini` | 메일의 뜻을 읽는 사람 | Intent, 요청사항, 요청자, 기한, 근거와 신뢰도 구조화 |
| M-02 | 기존 업무 장부를 찾는 검색 담당 | 현재는 동일 Thread 우선과 Metadata·Token 후보 검색 |
| M-03 Python | 회사 규칙을 지키는 판단 담당 | 후보 수·현재 상태·위험 변경을 보고 최종 Action 결정 |
| Pydantic·Validation | 잘못된 서류를 막는 검수 담당 | Schema, Task ID, 날짜, 상태 전이와 승인 정책 검사 |
| SQLite | 업무 장부 | Mail, Task, Link, History, Event와 사용자 결정 저장 |
| Streamlit | 사용자가 보는 업무 화면 | 업무 관리, 검토 요청, 타임라인과 운영 로그 표시 |
| 사용자 | 최종 책임자 | 완료·취소·기한 단축·복수 후보 같은 중요 결정 확정 |

LLM이 직접 DB를 수정하지 않는 이유는 잘못 읽은 결과가 실제 업무 상태를 훼손하지 않게 하기
위해서다.

## 3. 7개 Action과 5개 Status

### Action: Agent가 지금 무엇을 할지 정하는 명령

| Action | 뜻 | 예시 |
|---|---|---|
| `CREATE_TASK` | 새 업무 생성 | 처음 받은 서버 점검 요청 |
| `UPDATE_TASK` | 기존 업무 내용·기한·상태 변경 | 같은 업무의 기한 연장 |
| `LINK_TO_TASK` | 변경 없이 메일만 기존 업무에 연결 | 참고자료 도착 |
| `SET_WAITING` | 상대 회신·자료를 기다림 | 내가 자료 요청 메일을 보냄 |
| `MARK_COMPLETED` | 완료 변경을 제안 | “업무 완료 처리해 주세요” 수신 |
| `ASK_USER` | 자동 확정하지 않고 사람에게 질문 | 후보가 2개이거나 날짜가 모호함 |
| `IGNORE` | 업무관리 대상에서 제외 | 광고·공지·업무 무관 메일 |

### Status: Task가 현재 어느 상태인지 나타내는 값

`TODO → IN_PROGRESS → WAITING_REPLY → IN_PROGRESS → COMPLETED`

업무 취소 시에는 활성 상태에서 `CANCELLED`로 이동한다. 완료·취소는 중요한 변경이라 Agent의
제안만으로 확정하지 않고 사용자가 승인한다.

## 4. 현재 구현과 Task Context RAG의 차이

### 현재 동작

1. 같은 `conversation_id`면 같은 Thread이므로 기존 Task를 가장 먼저 찾는다.
2. Thread가 다르면 제목·요청자·요청요약 Token 점수를 계산한다.
3. 후보가 없거나 여러 개라서 확정할 수 없으면 안전하게 `ASK_USER`로 보낸다.

이 방식은 정의된 합성 Ground Truth의 단일 정답 연결 8/8을 통과했지만, “문구는 완전히
다르지만 실제로는 같은 업무”인 상황의 판단 깊이는 제한적이다.

### 최종 MVP에 남긴 Task Context RAG

```text
동일 Thread의 단일 활성 Task가 있음
  → 기존 결정론적 연결 유지

동일 Thread로 확정 불가
  → SQLite에서 활성 Task top-k 검색
  → 후보별 현재 상태 + 최근 Mail 3건 + History 5건 이하 구성
  → 별도 Task Context Agent가 SAME_TASK / NEW_TASK / AMBIGUOUS 판단
  → 저신뢰·모호함이면 Query를 한 번만 바꿔 재검색·재판단
  → 그래도 불확실하거나 오류면 ASK_USER
  → Python M-03과 기존 Validation이 최종 Action 확정
```

이것은 사내 문서검색용 Vector DB RAG가 아니다. 이미 저장된 Task·Mail·History를 필요한
범위에서 찾아 현재 Mail과 함께 판단하는 **Structured Task Context RAG**다.

## 5. 시연 전 준비 체크리스트

시연 20~30분 전에 아래 순서로 확인한다.

```powershell
# 1. 프로젝트 폴더에서 Health 확인
.\scripts\run_health.ps1

# 2. 자동 테스트는 시간이 허용될 때 한 번만 실행
.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider

# 3. Dashboard 실행
.\scripts\run_dashboard.ps1
```

브라우저 주소는 `http://localhost:8501`이다.

확인 항목:

- API Key나 OAuth Token을 화면·발표자료에 노출하지 않는다.
- Gmail 네트워크에 문제가 생겨도 합성 Dataset의 `MVP 시연 모드`로 시연할 수 있게 한다.
- 시연 직전에는 Windows 알림, 메일 팝업과 개인 화면을 닫는다.
- `MVP 시연 모드`와 `실제 업무 모드`의 DB가 분리된 이유를 한 문장으로 설명한다.
- 발표 중 Live 전체 평가를 새로 돌리지 않는다. 저장된 Evidence와 품질 검증 결과를 사용한다.

## 6. 가장 안전한 5분 시연 순서

### 0:00~0:30 — 문제와 한 문장 소개

말할 내용:

> 업무 메일은 새 요청으로 끝나지 않고 기한 변경, 자료 요청과 회신, 완료까지 이어집니다.
> MailTaskAgent는 메일을 요약하는 도구가 아니라 현재 Task 상태를 보고 다음 Action을 결정해
> 이 Lifecycle을 관리하는 Agent입니다.

### 0:30~1:00 — 구조 설명

화면: 첫 화면 또는 홈.

말할 내용:

> LLM은 메일 의미만 구조화하고 실제 Task 검색, 최종 Action과 DB 변경은 Python 정책과
> Validation이 담당합니다. 중요한 완료·취소·복수 후보는 사용자 승인 전 반영하지 않습니다.

### 1:00~2:00 — 신규 업무와 후속 변경

화면 순서:

1. `MVP 시연 모드` 진입
2. 필요하면 사이드바의 `데모 DB 초기화`
3. `데모 도구`의 `신규 업무 → 기한 변경` 실행
4. `내 업무` 또는 업무 상세에서 생성 Task와 변경된 기한 확인

말할 내용:

> 첫 메일은 기존 후보가 없어 `CREATE_TASK`가 되고, 같은 Thread의 다음 메일은 새 Task가
> 아니라 기존 Task의 `UPDATE_TASK`가 됩니다. 변경 전후와 근거 Mail이 History에 남습니다.

### 2:00~3:00 — 수신·발신 Lifecycle

화면: `자료 요청 → 회신 대기 → 자료 도착 후 재개` 데모와 Task Mail 타임라인.

말할 내용:

> 받은 메일만 보는 것이 아닙니다. 연결된 Gmail Thread에서 내가 보낸 자료 요청은
> `SET_WAITING`, 상대의 후속 회신은 다시 `IN_PROGRESS`로 이어집니다. 보낸편지함 전체가 아니라
> 이미 Task에 연결된 Thread만 읽기 전용으로 추적합니다.

### 3:00~4:00 — Human-in-the-loop와 로그

화면 순서:

1. `애매한 메일 → 사용자 확인` 실행
2. `검토 요청`에서 후보·근거 확인
3. 기존 Task 연결·신규 생성·무시 중 하나 선택
4. `운영 상태`에서 단계별 Event 확인

말할 내용:

> 후보가 두 개면 Agent가 임의 연결하지 않고 `ASK_USER`로 멈춥니다. 사용자 선택 이후에만
> DB가 바뀌고 Agent 제안과 사용자 최종 결정이 모두 History에 남습니다. 문제가 생기면 어느
> 단계에서 실패했는지 운영 로그로 확인할 수 있습니다.

### 4:00~5:00 — 검증 결과와 남은 과제

화면: `품질 검증` 또는 저장된 결과 요약.

말할 내용:

> 현재 기준선은 회사 LLM Live 15개 실행 단위, 28개 Action 단계, 테스트 Gmail 20건과
> 자동 테스트 122건을 통과했습니다. 이 수치는 정의된 합성·비식별 Dataset 기준입니다.
> 지난 멘토 피드백의 Task Context RAG는 최종 MVP 잔여 과제로 반영했습니다. 다른 표현의
> 동일 업무를 SQLite Context로 판단하고 한 번 재검색하되, 그래도 불확실하면 사용자에게
> 넘기는 구조입니다. 아직 구현 결과라고 말하지 않겠습니다.

## 7. Gmail Live를 보여줄 때의 선택 기준

Gmail Live는 연결 증거로는 좋지만 인터넷·OAuth·Scheduler 상태에 영향을 받는다. 내일의 핵심은
Agent 판단과 안전성 설명이므로 다음 원칙을 사용한다.

- Gmail 상태가 정상이고 이미 처리된 비식별 Mail이 보이면 30초 정도 실제 업무 모드에서
  연결 상태, 최근 Mail과 수신·발신 타임라인만 보여준다.
- 발표 중 새 메일을 즉석 발송하고 1분 Polling을 기다리는 것은 보조 시연으로만 사용한다.
- Gmail 연결이 늦거나 오류가 나면 즉시 MVP 시연 모드로 전환한다. 이것은 실패가 아니라
  Mail Adapter와 Agent Core가 분리돼 있다는 설계 장점이다.

## 8. 예상 질문과 답변

### “이게 왜 Agentic AI인가요?”

> 한 번 요약하고 끝나지 않고 현재 Task 상태를 조회해 7개 Action 중 다음 행동을 결정하고,
> 그 결과를 DB 상태로 남겨 다음 메일 판단에 다시 사용하기 때문입니다. 모호하면 사람에게
> 질문하고 결정 이후 Workflow를 이어가는 Human-in-the-loop도 포함합니다.

### “LLM이 다 판단하나요?”

> 아닙니다. 현재 LLM은 Mail 의미와 Intent를 구조화합니다. 최종 Action, 상태 전이와 DB 변경은
> Python Logic이 검증합니다. 추가할 Task Context Agent도 관계와 Action을 제안할 뿐 최종 권한은
> 갖지 않습니다.

### “RAG가 이미 구현됐나요?”

> 아닙니다. 현재 동작하는 기준선은 동일 Thread와 Metadata·Token Matching입니다. 멘토 피드백을
> 반영해 SQLite Task·Mail·History 기반 Task Context RAG를 최종 MVP 잔여 기능으로 설계했고,
> 구현·신규 테스트·전체 회귀 후 완료로 판정할 예정입니다.

### “왜 Vector DB를 안 쓰나요?”

> 현재 검색 대상은 대규모 사내 문서가 아니라 이미 구조화된 소수의 활성 Task와 최근 이력입니다.
> SQLite Context로 먼저 요구를 충족하고 설명 가능성과 범위를 유지합니다. 사내 문서 Corpus가
> 생기면 Vector DB는 Post-MVP에서 별도 검토합니다.

### “Gmail은 자동인가요? 버튼을 매번 누르나요?”

> 실제 업무 모드는 기본 1분 Polling으로 신규 Mail을 자동 확인하고, 수동 버튼은 즉시 확인이나
> 장애 점검용입니다. MVP 시연 모드의 버튼은 합성 메일 도착을 재현하는 테스트 장치입니다.

### “완료는 자동으로 바뀌나요?”

> Agent가 완료 근거를 발견하면 `MARK_COMPLETED`를 제안하지만 현재 안전 정책에서는 사용자가
> 승인해야 `COMPLETED`로 확정됩니다. 사용자가 Dashboard에서 직접 완료할 수도 있습니다.

### “메일 한 통에 요청이 여러 개면요?”

> 현재 계약은 한 Mail의 대표 업무 요청 하나와 Action 하나입니다. 독립 요청 자동 분해는
> 오분해 시 Task가 과도하게 생성될 위험이 있어 현재 최종 MVP에는 넣지 않았습니다.

### “현재 성능이 100%라는 뜻인가요?”

> 정의한 합성 Ground Truth의 측정 대상에서는 해당 분자·분모가 모두 일치했다는 뜻입니다.
> 실제 회사 Mailbox 전체 정확도나 실제 시간 절감률을 의미하지 않습니다.

## 10. 발표 직전 30초 암기 문장

> MailTaskAgent는 메일을 요약하는 도구가 아니라 Mail Thread와 현재 Task 상태를 보고 다음
> Action을 결정하는 개인 업무관리 Agent입니다. 현재 회사 LLM, 7개 Action, 5개 상태,
> Human-in-the-loop, SQLite History, Streamlit과 Gmail 파일럿까지 시연 가능한 Core 기준선을
