# 2026-09-02 MailTaskAgent 멘토 시연 상세 실행 스크립트

이 문서는 발표자료 설명이 끝난 뒤 실제 Dashboard를 시연할 때 그대로 따라 읽고 클릭할 수 있는
실행 대본이다. 실제 화면 명칭은 2026-09-01 현재 `http://localhost:8501`의 UI와 맞췄다.

## 0. 시연의 기본 원칙

- 먼저 `실제 업무 모드`에서 Gmail 연결과 운영형 UI를 약 3~4분 보여준다.
- 다음으로 `MVP 시연·검증 화면`에서 핵심 Agent Workflow를 약 5~7분 보여준다.
- 실제 업무 DB와 데모 DB는 분리되어 있다. `데모 DB 초기화`는 실제 Gmail 업무를 삭제하지 않는다.
- 실제 업무 모드에서는 `완료 처리`와 `사용자 결정 확정`을 누르지 않는다.
- MVP 시연 모드에서는 합성·비식별 데이터만 사용하며 필요하면 데모 DB를 초기화한다.
- Gmail이나 네트워크가 늦어도 MVP 시연 모드로 Agent Core를 독립 시연할 수 있다.
- API Key, OAuth Token, Authorization Header는 어떤 화면에서도 열거나 보여주지 않는다.

권장 전체 시간은 발표자료 7~8분, 실제 시연 8~10분, 질의응답 3~5분이다.

# 1부. 실제 업무 모드 · Gmail Live 시연

## Live 0단계 — Dashboard 접속

### 내가 할 동작

1. 브라우저에서 `http://localhost:8501`을 연다.
2. Gmail 연결이 되어 있으면 자동으로 `실제 업무 모드`의 `🏠 홈`이 열린다.
3. 왼쪽 사이드바가 접혀 있으면 펼친다.

### 화면에서 확인할 것

- 왼쪽 메뉴: `홈`, `내 업무`, `검토 요청`, `자동화 설정`, `운영 상태`, `설정`
- 사이드바: `Gmail 연결됨`, `Agent 실행` ON
- 홈 상단: `Agent 실행 중 · 1분 주기`

### 말할 문장

> 먼저 Gmail이 실제로 연결된 업무 화면입니다. 사용자가 메일마다 분석 버튼을 누르는 구조가
> 아니라, Agent 실행을 켜 두면 현재 설정된 주기에 따라 새 수신·발신 메일을 읽기 전용으로
> 확인합니다. 현재는 로컬 시연 환경이라 1분 Polling이고, 완전한 실시간 Push라고 표현하지는
> 않습니다.

### 정상 결과

- `Gmail 연결됨`
- `Agent 실행 중 · 1분 주기`
- `마지막 확인` 시각이 약 1분 주기로 갱신
- `최근 오류 0건`

### 문제가 생겼을 때

- 마지막 확인 시각만 멈췄으면 10초 정도 기다린다.
- Gmail 오류가 있으면 원인을 길게 해결하지 않고 “Mail Adapter와 Agent Core가 분리되어 있다”고
  설명한 뒤 MVP 시연 모드로 넘어간다.

## Live 1단계 — 홈에서 오늘 처리할 업무 설명

### 내가 할 동작

1. `🏠 홈`을 유지한다.
2. 상단 요약 카드와 `우선순위 업무` 목록을 가리킨다.
3. 어떤 `완료 처리` 버튼도 누르지 않는다.

### 화면에서 확인할 것

- `즉시 처리(P1)`
- `우선 처리(P2)`
- `회신 대기`
- `검토 요청`
- 각 업무의 색상, 상태, 기한, 요청자, 우선순위 근거

### 말할 문장

> 홈은 운영 로그가 아니라 사용자가 오늘 무엇을 먼저 처리해야 하는지 보는 화면입니다.
> 즉시 처리와 우선 처리는 Task의 우선순위이고, 회신 대기는 Task의 현재 상태, 검토 요청은
> Agent가 자동 반영을 중단하고 사용자의 결정을 기다리는 항목입니다. 목록은 기한과 회신 대기의
> 긴급도, VIP·고객사·키워드·사용자 지정 중요도를 함께 반영해 정렬합니다.

> 화면의 숫자는 메일 개수가 아니라 현재 Task 기준입니다. 후속 메일이 기존 업무와 관련되면
> 새 Task를 계속 만드는 것이 아니라 같은 Task에 연결해 상태와 History를 갱신합니다.

### 멘토가 “P1은 어떻게 정합니까?”라고 물으면

> 기한 초과나 오늘 마감은 긴급도를 가장 높게 보고, 기한 임박과 장기 회신 대기는 다음 단계로
> 반영합니다. VIP 발신자, 고객사 도메인, 중요 키워드와 사용자가 직접 지정한 중요도는 별도
> 중요도 신호입니다. 두 값을 조합해 P1부터 P4까지 계산하며 상세 근거도 화면에 표시합니다.

## Live 2단계 — Mail과 Task의 차이 확인

### 내가 할 동작

1. 왼쪽 메뉴에서 `✅ 내 업무`를 누른다.
2. `서버 4대 패치 적용 여부 확인` 업무를 찾는다.
3. 해당 카드의 `상세 보기`를 누른다.

### 화면에서 확인할 것

- 큰 `업무 상세` 팝업
- `메일 진행 타임라인`
- `업무 변경 기록`
- 하단의 제목·설명·상태·기한·회신 필요·중요도 수정 영역

### 말할 문장

> Mail은 수신하거나 발신한 개별 메시지이고, Task는 관련 메일 여러 통을 하나의 업무로 묶어
> 관리하는 단위입니다. History는 메일에 따라 Task의 내용과 상태가 어떻게 바뀌었는지 남긴
> 감사 기록입니다.

> 상세 보기에서는 메일 타임라인, Agent Action, 당시 상태, 변경 전후 값과 판단 근거를 함께
> 볼 수 있습니다. 사용자가 직접 상태나 기한을 수정해도 그 변경이 History에 남습니다.

## Live 3단계 — 수신·발신 Thread Lifecycle 설명

### 내가 할 동작

1. 열린 `업무 상세` 팝업의 `메일 진행 타임라인`을 위에서 아래로 읽는다.
2. 첫 번째 `받은 메일`과 두 번째 `보낸 메일`을 차례로 가리킨다.
3. 팝업 하단의 저장 버튼은 누르지 않는다.

### 화면에서 확인할 것

```text
받은 메일: [LIVE-DEMO] 서버 패치 결과 확인 요청
→ CREATE_TASK
→ 상태: 할 일

보낸 메일: Re: [LIVE-DEMO] 서버 패치 결과 확인 요청
→ SET_WAITING
→ 상태: 회신 대기
```

### 말할 문장

> 첫 수신 메일은 서버 패치 결과를 확인해 달라는 신규 요청이라 CREATE_TASK가 되었습니다.
> 이후 제가 업무 수행에 필요한 자료를 요청하는 회신을 보냈고, Agent는 발신함의 같은 Gmail
> Thread를 확인해 새 Task가 아니라 기존 Task에 연결하고 SET_WAITING으로 바꿨습니다.

> 따라서 지금 보이는 것은 메일 두 통, Task 한 개입니다. 이후 상대방이 같은 Thread로 자료를
> 보내면 그 메일도 같은 Task에 연결되고 진행 중으로 복귀할 수 있습니다. 신규 요청, 기한 변경,
> 자료 요청, 자료 도착이 모두 반드시 순서대로 있어야 완료되는 것은 아니며, 실제로 발생한 변화만
> 현재 Task에 누적됩니다.

## Live 4단계 — Human-in-the-loop Queue 설명

### 내가 할 동작

1. 업무 상세 팝업의 `X`를 눌러 닫는다.
2. 왼쪽 메뉴에서 `🔔 검토 요청`을 누른다.
3. 확인 대기 항목 하나를 선택하되 `사용자 결정 확정`은 누르지 않는다.

### 화면에서 확인할 것

- Agent 판단 근거
- 후보 Task
- 사용자 선택지
- 사용자 확정 전 자동 반영 중단 안내

### 말할 문장

> 후보가 여러 개이거나 중요한 상태 변경을 확신할 수 없으면 Agent가 임의로 연결하지 않고
> ASK_USER로 멈춥니다. 사용자가 기존 Task 연결, 신규 Task 생성, 무시 중 하나를 선택한 뒤
> 확정해야 DB에 반영됩니다. Agent 제안과 사용자 최종 결정은 모두 History에 남습니다.

## Live 5단계 — 개인 우선순위와 제외 규칙 설명

### 내가 할 동작

1. 왼쪽 메뉴에서 `⚙️ 자동화 설정`을 누른다.
2. `⭐ 우선순위 기준` 탭을 보여준다.
3. `🚫 광고·반복 메일 제외` 탭을 보여준다.
4. `⚙️ 실행 주기` 탭을 보여준다.
5. 값은 변경하거나 저장하지 않는다.

### 화면에서 확인할 것

- 기한 임박·예정 업무·회신 대기 시간 기준 3개
- VIP 발신자·고객사 도메인·중요 키워드 Rule
- 정확한 발신자·도메인·제목 키워드 기반 제외 Rule
- 새 메일 확인 주기

### 말할 문장

> 사용자마다 중요한 고객사와 업무 기준이 다르기 때문에 우선순위 규칙을 직접 설정할 수 있습니다.
> 숫자 3개는 전체 기준이 아니라 기한과 회신 대기의 조정 가능한 시간 경계값입니다. 그 아래의
> VIP 발신자, 고객사 도메인, 중요 키워드와 업무별 사용자 직접 지정 중요도도 계산에 포함됩니다.

> 광고·뉴스레터·자동발송 메일은 정확한 발신자, 도메인 또는 제목 키워드 규칙으로 제외할 수
> 있습니다. 본문의 단어 하나만으로 업무를 위험하게 제거하지 않으며 제외 결과도 처리 기록에
> 남깁니다.

# 2부. MVP 시연·검증 화면 · 합성 데이터 시연

## MVP 0단계 — 시연 모드 전환과 격리 설명

### 내가 할 동작

1. 실제 업무 모드 왼쪽 아래의 `MVP 시연·검증 화면`을 누른다.
2. 사이드바에서 `LIVE · gpt-4.1-mini`를 가리킨다.
3. 입력 Source가 `합성 데모`인지 확인한다.

### 화면에서 확인할 것

- `MVP 시연·검증`
- `LIVE · gpt-4.1-mini`
- 입력 Source: `합성 데모`
- `합성 Mail 15건 · 전체 Agent Core 검증`
- 탭: 업무 현황, 메일 처리함, 확인 필요, 운영 로그, 품질 검증, 데모 도구

### 말할 문장

> 이 화면은 실제 Gmail 업무와 섞이지 않는 합성·비식별 시연 환경입니다. 화면과 DB는 분리하지만
> 회사 LLM, Workflow, Validation과 Application Logic은 실제 업무 모드와 같은 Agent Core를
> 사용합니다. 따라서 데모를 반복해도 실제 업무 데이터에는 영향을 주지 않습니다.

## MVP 1단계 — 데모 DB 초기화

### 내가 할 동작

1. 사이드바의 `데모 DB 초기화`를 한 번 누른다.
2. 초기화 후 `데모 도구` 탭으로 이동한다.

### 말할 문장

> 각 시나리오는 이전 결과와 섞이지 않도록 격리된 데모 DB를 초기화하고, 정의된 합성 메일을
> 실제 도착 순서대로 투입합니다.

### 주의

- `데모 DB 초기화`는 시연 시작 시 한 번만 누른다.
- 실제 업무 모드의 Gmail Task DB에는 영향을 주지 않는다.

## MVP 2단계 — 신규 업무와 기한 변경 시연

### 내가 할 동작

1. `데모 도구` 탭에서 `신규 업무 → 기한 변경` 영역을 찾는다.
2. 그 영역의 `이 시나리오 실행`을 누른다.
3. 실행 완료 후 `업무 현황` 탭으로 이동한다.
4. `Task History`에서 `MAIL-001 · CREATE_TASK`와 `MAIL-002 · UPDATE_TASK`를 확인한다.

### 화면에서 확인할 것

```text
MAIL-001 → CREATE_TASK
MAIL-002 → UPDATE_TASK
```

### 말할 문장

> 첫 메일은 연결할 기존 업무가 없으므로 CREATE_TASK가 됩니다. 같은 Thread의 후속 메일은
> 새 업무를 만들지 않고 기존 Task의 기한을 바꾸는 UPDATE_TASK가 됩니다. 변경 전후 값,
> Source Mail ID, 판단 근거와 처리 시각은 History에 남습니다.

## MVP 3단계 — 회신 대기와 업무 재개 시연

### 내가 할 동작

1. `데모 도구` 탭으로 돌아간다.
2. `회신 대기 → 업무 재개` 영역의 `이 시나리오 실행`을 누른다.
3. 실행 완료 후 `업무 현황`에서 Task 상태와 History를 확인한다.

### 화면에서 확인할 것

```text
MAIL-001 → CREATE_TASK
MAIL-003 → SET_WAITING
MAIL-004 → UPDATE_TASK / 진행 재개
```

### 말할 문장

> 신규 요청으로 Task가 생성된 뒤 사용자가 자료를 요청해 보낸 메일은 SET_WAITING으로 회신
> 대기 상태를 만듭니다. 상대방이 자료를 보내면 같은 Task에 연결되고 다시 진행 중으로
> 복귀합니다. 받은편지함만 보는 것이 아니라 연결된 발신 Mail도 Lifecycle 판단에 사용합니다.

## MVP 4단계 — 애매한 메일과 ASK_USER 시연

### 내가 할 동작

1. `데모 도구` 탭으로 돌아간다.
2. `애매한 메일 → 사용자 확인` 영역의 `이 시나리오 실행`을 누른다.
3. 회사 LLM 처리가 끝날 때까지 약 15~30초 기다린다.
4. `확인 필요` 탭으로 이동한다.
5. `확인할 Mail`에서 `MAIL-006`을 선택한다.
6. 후보와 선택지를 보여주되, 시간이 부족하면 `사용자 결정 확정`은 누르지 않는다.

### 화면에서 확인할 것

- `ASK_USER`
- 관련 활성 Task 후보 2개
- `기존 Task 연결`
- `신규 Task 생성`
- `무시`
- `사용자 결정 확정`

### 말할 문장

> 이 메일은 연결 가능한 활성 Task 후보가 두 개이므로 Agent가 임의로 하나를 선택하지 않습니다.
> ASK_USER로 자동 반영을 멈추고 사용자가 기존 Task 연결, 신규 Task 생성, 무시 중 하나를
> 선택하도록 합니다. 사용자 확정 전에는 Task DB를 변경하지 않는 Fail-closed 구조입니다.

### 실제 확정까지 보여줄 경우

1. `기존 Task 연결`을 선택한다.
2. 후보 Task 하나를 선택한다.
3. `사용자 결정 확정`을 누른다.
4. `업무 현황`의 History에서 Agent 제안과 사용자 최종 결정을 확인한다.

## MVP 5단계 — 완료 제안과 승인 Gate 설명

### 내가 할 동작

1. 시간이 충분하면 `데모 도구` 탭으로 돌아간다.
2. `완료 제안 → 사용자 승인` 영역의 `이 시나리오 실행`을 누른다.
3. `확인 필요`에서 완료 제안과 승인 전 상태를 보여준다.

### 말할 문장

> 완료 근거가 있는 메일을 받아도 Agent가 Task를 즉시 완료하지 않습니다. MARK_COMPLETED는
> 제안이고, 현재 안전 정책에서는 사용자가 승인해야 COMPLETED로 확정됩니다. 취소와 기한 단축도
> 같은 방식으로 사용자 승인 Gate를 유지합니다.

## MVP 6단계 — Agent 실행 로그 설명

### 내가 할 동작

1. `운영 로그` 탭을 누른다.
2. `Agentic Workflow Trace`에서 방금 처리한 Mail ID를 선택한다.
3. `Observe Input / Analyze → Act / Retrieve → Observe Context → Re-evaluate / Decide →
   Python Guard → Act / Execute → Observe Result → Final Output` 순서를 위에서 아래로 보여준다.
4. `STRUCTURED_RAG` 경로이면 검색 후보 ID·점수·근거, Task 상태, 최근 Mail·History 수,
   관계·추천 Action·신뢰도와 재검색 횟수를 가리킨다.
5. 아래의 Mail ID, Level, 처리 단계 Filter와 `상세 로그`를 보여준다.
6. 필요하면 `Audit 원문 · 정제된 기술 데이터`를 펼친다.

### 화면에서 확인할 것

- 정제된 Mail 입력과 M-01 Mail 분석
- SQLite top-k 검색과 후보 Context 관찰
- Task 관계·추천 Action·신뢰도, 필요 시 Query Rewrite 1회
- Python Guard와 실제 DB 실행 결과 재조회
- M-01~M-05 처리 단계
- SUCCESS/FAILED
- 처리 시각과 판단 근거
- Source Mail ID와 Case ID
- Secret 제거 문구

### 말할 문장

> 이 Trace는 입력 관찰, SQLite Context 검색, 후보 상태와 History 관찰, LLM 관계 판단, 필요 시
> Query Rewrite와 재판단, Python Guard, Action 실행, 저장 결과 재조회까지 시간순으로 보여줍니다.
> 원시 Chain-of-Thought를 노출하는 화면이 아니라 입력·검색·판단·도구 실행의 검증 가능한 증거를
> 보여주는 Processing Event입니다. 문제가 생기면 실패 지점을 찾을 수 있고 Secret은 저장하지
> 않습니다.

## MVP 7단계 — 저장된 품질 검증 결과 설명

### 내가 할 동작

1. `품질 검증` 탭을 누른다.
2. 발표 중 `회사 LLM Live 15개 검증`을 새로 실행하지 않는다.
3. `표시할 결과`가 `회사 LLM Live`인지 확인한다.
4. 저장된 결과 수치를 가리킨다.

### 화면에서 확인할 것

- 통과 시나리오: 15/15
- Action 단계: 28단계, 100%
- 업무 요청 분류: 100%
- 요청사항·기한 추출: 100%
- 기존 Task 연결: 100%
- Intent 진단: 86.7%
- 실제 업무 정리시간은 아직 사용자 측정 전

### 말할 문장

> 저장된 회사 LLM Live 결과는 15개 대표 시나리오와 28개 Action 단계가 모두 기대 결과와
> 일치했습니다. 업무 요청 분류 15/15, 요청사항과 기한 추출 26/26, 단일 정답 Task 연결 8/8도
> 확인했습니다. 다만 이것은 정의한 합성 Ground Truth 범위의 결과이며 실제 회사 Mailbox 전체
> 정확도 100%를 의미하지 않습니다.

> Intent 진단은 86.7%로 별도 표시하고 있습니다. 또 업무 정리시간 30% 단축은 사람의 실제
> 수동 처리시간 측정이 끝나지 않았으므로 달성값으로 말하지 않습니다.

## MVP 8단계 — 최종 Agentic AI 보강 결과 마무리

### 말할 문장

> 현재 회사 LLM, M-01부터 M-05, 7개 Action, 5개 Status, Human-in-the-loop, SQLite History,
> Streamlit Dashboard와 Gmail 수신·발신 파일럿까지 연결한 Core E2E를 검증했습니다.

> 동일 Thread로 확정할 수 없는 경우에는 SQLite의 활성 Task·최근 Mail·History Context를
> top-k로 검색하고, 별도 Task Context Agent가 관계와 Action을 제안합니다. 저신뢰면 Query를
> 최대 한 번 재작성·재검색하며, 그래도 불확실하거나 오류가 나면 ASK_USER로 안전하게
> 종료합니다. Python Guard가 최종 Action을 검증하고 DB 반영 뒤 실제 저장 상태도 다시 조회합니다.

> 화면의 Agent 실행 로그에서는 정제된 입력, 검색 후보와 점수, 관계 판단, 재검색 여부,
> Python Guard, 실행 결과 관찰과 최종 결과를 시간순으로 확인할 수 있습니다. 원시 Chain-of-Thought와
> Secret은 기록하지 않습니다. 전체 pytest 136개와 회사 LLM Live 합성 검증 3/3을 통과했습니다.

> Outlook, 사내 인증, 서버 운영 DB, 회사 문서 RAG는 그 이후 Post-MVP입니다.

# 3부. 시연 중 자주 생기는 상황별 대응

## Gmail 마지막 확인 시각이 바로 바뀌지 않을 때

> Gmail 수집 주기는 1분이고 상단 상태 표시는 10초마다 최신 실행 기록을 다시 읽습니다.
> 최대 한 주기 정도 기다리면 갱신됩니다.

## 회사 LLM 시나리오가 10초 이상 걸릴 때

> 지금은 실제 회사 LLM Live 호출이므로 여러 단계의 분석이 순차 실행되고 있습니다. 저장된
> 품질 Evidence는 이미 검증되어 있고, 네트워크 상태와 무관한 Mock 회귀도 별도로 유지합니다.

## Gmail 연결 오류가 날 때

> Gmail은 입력 Adapter이고 Agent Core와 분리되어 있습니다. 지금은 합성 데이터 시연 모드로
> 동일 Workflow를 보여드리겠습니다.

## 완료 여부를 질문받을 때

> Core E2E와 Task Context RAG·최대 1회 ReAct 재판단·Agent Trace까지 구현·검증해 AI Master
> 최종 MVP 기술 Gate를 완료했습니다. Outlook과 사내 운영환경은 Post-MVP입니다.

## “왜 한 번에 메일 전체를 LLM에 주지 않나요?”라고 물을 때

> 개인정보와 비용, Prompt Injection 위험을 줄이고 설명 가능성을 유지하기 위해 전체 Mailbox를
> LLM에 전달하지 않습니다. 확정 가능한 Thread Metadata를 우선하고, 필요한 활성 Task의 제한된
> 최근 Context만 전달합니다.

## 시연 종료 문장

> MailTaskAgent의 핵심은 메일 요약이 아니라 현재 Task 상태를 읽고 다음 Action을 결정하며,
> 중요한 변경은 사용자에게 확인하고 그 결과를 다음 판단에 다시 사용하는 Agentic Workflow입니다.
