# 09285 백준현 MailTaskAgent 최종 시연 스크립트

## 1. 시연 원칙

- 본편은 **실제 Gmail + 회사 LLM Live + 실제 업무 모드**로 진행한다.
- `MVP 시연·검증` 화면은 마지막에 자동 테스트와 반복 검증 근거로 약 10초만 보여준다.
- 영상에서 Mock 시나리오를 새로 실행하지 않는다.
- 원시 Chain-of-Thought는 보여주지 않는다. 입력 요약, 검색 후보, 판단 근거, Action Proposal, Python Guard, DB 관찰 결과만 설명한다.
- 테스트 계정, 합성 업무 메일, Allowlist 수신자만 사용한다.

## 2. 녹화 전 준비

1. Streamlit `http://localhost:8501` 접속
2. 상단 상태에서 `Agent 실행 중`, `Gmail 연결됨`, 마지막 확인 시각 확인
3. 설정에서 회사 LLM `LIVE`, Gmail Read/Send 준비 상태 확인
4. 브라우저 확대 100%, 개인정보가 있는 다른 탭과 알림 닫기
5. 실제 업무 DB는 초기화하지 않는다.
6. 이번 검증에 사용할 제목 Marker를 메모한다.

## 3. 5분 시연 순서와 대사

### 0:00~0:25 문제와 입력

화면: Gmail 테스트 계정

대사:

> MailTaskAgent는 메일 요약기가 아니라 메일을 업무로 해석하고 기존 Task 상태를 함께 본 뒤 다음 행동을 결정하는 개인 업무관리 Agent입니다. 지금 별도 테스트 계정에서 합성 업무 요청을 보내 실제 수집부터 Task 생성까지 보여드리겠습니다.

신규 메일 예시:

```text
제목: [MTA-DEMO] 신규 테스트 서버 점검 요청
본문: 테스트 서버 2대의 점검 가능 일정을 2026년 9월 16일까지 회신해 주세요.
```

성공 확인: Gmail에서 전송 완료, 수신 계정의 제한 라벨에 메일 표시.

### 0:25~1:15 자동 수집과 Task 생성

화면: MailTaskAgent 홈

조작:

1. 자동 갱신 후 새 업무가 나타날 때까지 기다린다.
2. 새 Task의 제목, 요청자, 기한, 우선순위 근거를 확인한다.
3. 홈의 업무 제목 영역을 클릭해 해당 업무의 상세창을 연다. `완료 처리`는 누르지 않는다.

대사:

> Scheduler가 Gmail 제한 라벨을 주기적으로 확인합니다. 새 Mail ID만 회사 LLM으로 분석하며, 이미 처리한 ID는 다시 실행하지 않습니다. 방금 메일은 NEW_TASK로 분석되어 TODO Task가 자동 생성됐고, 요청 기한과 회신 필요 여부가 함께 저장됐습니다.

성공 확인: 신규 Task, `CREATE_TASK`, 기한 `2026-09-16`, 사용자 검토 대기 없음.

### 1:15~2:40 Agent 판단 과정

화면: `업무 상세`의 Mail 흐름과 `Agent 판단` 또는 운영 Trace

조작:

1. Mail 흐름에서 메일 행을 클릭해 본문·발신자·수신자를 확인한다.
2. Trace에서 M-01부터 최종 출력까지 순서대로 펼친다.
3. 운영 상태의 시스템 로그에서 `GMAIL-1a09aa6b60e7991f`를 선택해 실제 `STRUCTURED_RAG` Case를 보여준다.

대사:

> M-01은 메일의 의미, Intent, 요청, 기한을 구조화합니다. 같은 Gmail Thread의 단일 활성 Task는 확정 경로로 연결합니다. 확정할 수 없을 때 M-02가 SQLite의 활성 Task, 최근 Mail, History를 top-k로 검색합니다. 별도 Task Context Agent가 SAME_TASK, NEW_TASK, AMBIGUOUS와 다음 Action을 제안합니다. 첫 판단이 낮은 신뢰도이면 검색어를 한 번만 바꿔 재검색하고 다시 판단합니다.

> 화면의 신뢰도는 LLM의 자기보고 값이지 검증된 정확도 확률은 아닙니다. 실제 자동 실행 여부는 Python Safety Guard가 후보 ID, Intent, 상태 전이, 중요 변경과 Payload를 검증해 결정합니다.

성공 확인: SQLite RAG 후보 5개, Agent의 `NEW_TASK`·`CREATE_TASK` 제안과 자기보고 신뢰도 0.95,
Python Guard의 Intent 불일치 차단, 최종 `ASK_USER`가 서로 구분되어 보임. 이 Case는 재검색이 발생한
사례가 아니므로 Query Rewrite를 실행한 것처럼 설명하지 않는다.

### 2:40~3:30 Human-in-the-loop

화면: 검토 요청

대사:

> 후보가 여러 개이거나 판단이 불확실하면 Agent는 DB를 바꾸지 않고 ASK_USER로 멈춥니다. 완료, 취소, 기한 단축처럼 영향이 큰 변경은 신뢰도가 높아도 자동 확정하지 않습니다. 사용자가 기존 Task 연결, 신규 생성, 무시 또는 제안 승인을 선택한 결과가 History에 함께 남습니다.

성공 확인: 사용자 결정 전 Task 미변경, 결정 후 Task와 History 반영.

### 3:30~4:20 AI 회신과 승인 발송

화면: 업무 상세의 `AI 회신 준비`

조작:

1. 아직 판단 기록이 없다면 `회신 방식 판단`을 누르고 완료될 때까지 기다린다.
2. Agent가 판단한 회신 방식과 자기보고 신뢰도를 확인한다.
3. 필요한 날짜 또는 값을 입력하고 초안을 생성한다.
4. 수신자, 원본 Thread, 제목, 본문을 확인한다.
5. 실제 발표에서는 준비된 발송 증적을 설명한다. Live 발송은 테스트 수신자 확인 후에만 수행한다.

대사:

> 회신 Agent는 NO_REPLY, SIMPLE_ACK, DATE_REPLY 같은 방식을 선택하고 필요한 사용자 입력만 요청합니다. 초안은 자동 발송되지 않습니다. 원본 Gmail Thread와 Allowlist 수신자를 잠그고 사용자가 최종 승인해야 발송합니다. 성공 후 Task는 WAITING_REPLY로 바뀌며 발송 History가 저장됩니다.

성공 확인: 승인 전 발송 없음, 승인 발송 후 Gmail Thread·History·WAITING_REPLY 일치.

### 4:20~4:40 실행 결과 관찰과 중복 방지

화면: 운영 상태 또는 Agent Trace

대사:

> DB 실행 후 Task를 다시 조회해 기대 상태와 실제 상태가 일치하는지 관찰합니다. 같은 Gmail 메일을 다시 조회하면 이미 처리된 35건을 모두 중복으로 판정했고 Task와 History를 추가하지 않았습니다.

### 4:40~4:50 시연·검증 화면

화면: `MVP 시연·검증`의 품질 결과

대사:

> 이 화면은 실제 Gmail 시연을 대신하는 화면이 아니라 반복 가능한 검증 근거입니다. 현재 전체 pytest 179개, 회사 LLM Live 15개 Case와 28개 Action 단계가 통과했습니다.

Mock Case 실행 버튼은 누르지 않고 결과만 보여준다.

### 4:50~5:00 마무리

대사:

> 최종 MVP는 Mail-to-Task, Task Context RAG, 제한적 ReAct, Agent Action Proposal, Python Guard, Human-in-the-loop, Trace와 사용자 승인 Gmail 발송까지 포함합니다. Outlook과 사내 인증·서버 운영은 Post-MVP 범위입니다.

## 4. 제출 영상 2분 50초 구성

제출 영상은 위의 5분 Live 시연을 그대로 길게 녹화한 파일이 아니라, 공식 제출 가이드에 맞춰
검증된 화면과 로그를 압축 편집한 별도 파일이다.

### 0:00~0:30 시나리오 소개

- 전면 타이틀: `1. 시나리오 소개`
- 실제 Gmail 합성 업무가 Task로 생성된 홈과 업무 상세를 보여준다.
- 원문·발신자·수신자·Gmail Mail ID, M-01 구조화 결과를 확인한다.
- 성공 기준은 Task 생성·연결, 회신 방식 판단, 사용자 승인 후 Gmail 저장이다.

### 0:30~1:22 Mail 분석과 회신 준비

- M-01 회사 LLM의 요청·기한·Intent 구조화를 설명한다.
- Reply Agent의 `DATE_REPLY`와 0.95 자기보고 신뢰도를 정확도와 구분한다.
- 사용자 승인 전에는 발송하지 않는 안전 정책을 설명한다.

### 1:22~2:24 Agent 추론 로그 핵심

- 전면 타이틀: `2. Agent 추론 로그 (핵심)`
- Dashboard Trace에서 SQLite RAG, Context 관찰, Agent Action Proposal, Python Guard를 보여준다.
- 실제 `processing_events` 콘솔 화면으로 동일 실행의 고수준 Event를 다시 확인한다.
- Query Rewrite는 해당 Gmail 실행에서 발생한 것처럼 말하지 않는다. 별도로 표시한 합성·비식별
  회사 LLM Live `LIVE-RAG-02`, `LIVE-RAG-03`의 1회 재검색·재판단 증적이라고 설명한다.
- 원시 Chain-of-Thought가 아니라 구조화된 판단 근거와 Tool 입력·출력을 표시한다.

### 2:24~2:50 최종 결과 확인

- 전면 타이틀: `3. 최종 결과 확인`
- 회사 LLM Live 15/15, Action 28/28, pytest 179 passed를 보여준다.
- 실제 Gmail 수집·사용자 승인 발송·동일 Thread 저장·`WAITING_REPLY`·중복 방지는 별도 E2E
  Evidence로 검증했다고 설명한다.
- Outlook·사내 인증·서버 운영은 Post-MVP임을 분명히 한다.

영상에는 한국어 Microsoft Neural 음성과 삽입 자막이 함께 들어간다. 음성은 이해 보조 수단이며,
화면과 자막의 구현 사실을 넘어서는 주장을 추가하지 않는다.

## 5. 문제가 생겼을 때 대처

| 상황 | 대처와 설명 |
|---|---|
| 새 메일이 바로 안 보임 | 마지막 확인 시각을 보고 최대 한 주기를 기다린 뒤 새로고침. 임의로 DB 초기화하지 않음 |
| Gmail 동기화 중 | 중복 Scheduler 실행을 기다림. `SyncAlreadyRunning`은 데이터 손상 오류가 아님 |
| Task Context·Reply 판단 LLM 오류 | Fail-closed로 `ASK_USER` 전환되고 Task가 변경되지 않았는지 확인 |
| M-01 Mail 분석 API·Schema 최종 실패 | 처리 상태가 `FAILED`로 기록되고 Task가 생성·변경되지 않았는지 확인한 뒤 운영 상태에서 재처리 가능 여부를 설명 |
| 신뢰도가 높지만 검토 요청 | 중요 변경 승인 Gate가 신뢰도보다 우선한다고 설명 |
| 네트워크 지연 | 이미 확보한 Trace와 Evidence 화면으로 전환하고 검증 범위를 명확히 말함 |
